# 项目背景与目标

> 版本：0.1
> 状态：立项与侦察阶段
> 更新日期：2026-10-24

> 历史立项基线：本文的环境与假设清单未逐项滚动更新。引擎、设备和当前证据以 `AGENTS.md` 与 `analysis/notes/` 为准；2026-10-25 的完整系统范围、后续优先级与验收以 [04-system-roadmap.md](04-system-roadmap.md) 为准。图鉴、天极角色与法阵进入后续版本，专属武器延期。

## 1. 项目背景

项目发起人希望在自己的 Android 设备或电脑模拟器上，重新做一个可以独立游玩的《命运圣契》风格 3D 游戏。目标不是运营一款商业手游，也不是复制原游戏的服务器、账号体系、付费系统和全部内容，而是理解其可观察的核心玩法后，用新的代码和可控资产完成一个私用原型。

原游戏只作为本地研究对象。原 APK、资源、角色、音频、商标和受版权保护的素材不进入最终可分发包。最终项目使用自制占位资产、开放授权资产或已获授权的素材。

## 2. 已确认事实与待验证假设

### 已确认事实

- 平台为 Android。
- 使用 MuMu 模拟器运行。
- 用户描述为单机，但“单机”可能仍包含登录、资源下载或服务端状态，需要实测确认。
- 用户描述为 3D，最终引擎识别结果以 APK、日志和运行表现为准。
- 当前工作目录为 `F:\projects\FateCovenantClone`。
- 项目初期使用 Windows 环境上的 ADB、REA 和 Unity 工具链。

### 待验证假设

- 游戏使用 Unity 引擎，可能为 IL2CPP 构建。
- 核心循环由“角色获取或养成、编队、关卡战斗、奖励结算”组成。
- 战斗可能是自动战斗、回合制或半即时制，当前不能确定。
- 角色、技能和关卡数据可能来自本地配置或远程 AssetBundle。
- 关键进度可能依赖服务器，无法仅靠客户端存档完整重建。
- 模拟器内的 APK 可能是 split APK，资源可能分散在 base、asset 和 native split 中。

这些假设必须通过截图、视频、日志、APK 结构、IL2CPP 元数据和实际交互逐项确认。

## 3. 问题定义

要在有限时间内做出“像原游戏”的体验，必须解决三个问题：

1. **理解问题**：原游戏的核心反馈、战斗规则、界面流程和数值目标是什么。
2. **表达问题**：如何用 3D 角色、镜头、动画、UI、特效和音效重现这些反馈。
3. **工程问题**：如何用 Unity 把这些系统组织成可测试、可扩展、能稳定运行在 Android 上的项目。

首要风险不是“不会写代码”，而是把大量时间投入到未被验证的功能。项目必须以可复现证据和可玩的纵向切片推进。

## 4. 产品愿景

做一个短小、完整、可重复游玩的 3D 小队战斗原型。用户打开应用后，可以查看角色、编成队伍、进入关卡、完成一场有技能表现和胜负反馈的战斗、获得奖励并保存进度。

首个版本不追求内容数量，而追求：

- 从启动到结算没有断裂。
- 核心战斗具有清楚的策略和反馈。
- 画面具有统一的方向感，而不是素材堆砌。
- 结构允许后续增加角色、技能、敌人和关卡。

## 5. 项目目标

### 5.1 北极星目标

交付一个可在 Android 上安装并独立运行的 3D 小队战斗纵向切片，具备完整的一局游戏闭环，且代码和资产可以持续扩展。

### 5.2 阶段目标

| 优先级 | 目标 | 可验证结果 |
| --- | --- | --- |
| P0 | 建立可复现的分析环境 | ADB、截图、日志、APK、REA 和 Unity 工具链可用 |
| P0 | 确认原游戏核心循环 | 有一份基于截图、视频和日志的玩法事实清单 |
| P0 | 建立 Unity Android 工程 | 空场景可构建、安装、启动 |
| P1 | 完成战斗纵向切片 | 3 名角色、1 个敌人组、1 个关卡、胜负和结算 |
| P1 | 完成本地存档 | 重启应用后编队和进度保留 |
| P1 | 完成基础 3D 表现 | 角色站位、移动或待机、技能、受击、镜头和特效 |
| P2 | 建立内容管线 | 新角色、技能、敌人和关卡可通过数据配置增加 |
| P2 | 完成基础养成 | 等级、经验或一套经确认的成长系统 |
| P3 | 美术替换和性能优化 | 稳定帧率、可接受的内存和安装包体积 |

### 5.3 非目标

- 不实现原游戏的商业运营、充值、广告、抽卡付费或账号交易。
- 不还原完整主线、全部角色、全部关卡和全部活动。
- 不连接或破解原游戏服务器。
- 不在首版实现多人、公会、排行榜或跨设备云存档。
- 不把原游戏资源直接打包进最终 APK。
- 不在未确认战斗类型前锁定复杂战斗框架。

## 6. 用户与使用场景

### 目标用户

当前只有项目发起人，目标是在电脑模拟器和 Android 设备上反复游玩自己制作的版本。

### 核心场景

1. 启动游戏，进入主界面。
2. 查看已有角色和基础属性。
3. 选择角色组成队伍。
4. 选择关卡并进入战斗。
5. 观察技能、伤害、状态和胜负。
6. 获得奖励并返回主界面。
7. 关闭应用后重新打开，进度仍然存在。

### 次级场景

- 更换队伍并比较战斗结果。
- 重复挑战关卡。
- 后续增加新角色、技能和敌人。
- 在编辑器中快速测试单场战斗。

## 7. 产品原则

1. **先证据，后实现**：没有看到的机制不进入核心代码。
2. **先闭环，后内容**：一关完整比十个半成品界面重要。
3. **先占位，后美术**：系统跑通后再替换角色和特效。
4. **数据驱动**：角色、技能、敌人和关卡不硬编码在 MonoBehaviour 中。
5. **本地优先**：默认离线可玩，网络只作为可选未来能力。
6. **可测试**：战斗结算和存档有确定性测试，不依赖随机观察。
7. **资产隔离**：分析资料、原资源、自制资源和最终构建包分开存放。
8. **小步提交**：每个改动都能回到可运行状态。

## 8. 范围

### 首版必须包含

- 启动场景和主界面。
- 角色数据与角色展示。
- 三人编队。
- 一个可重复挑战的关卡。
- 一场有技能、伤害、受击、死亡和胜负的战斗。
- 战斗结算和奖励。
- 本地存档和版本迁移入口。
- Android APK 构建、安装和运行。

### 首版可以延后

- 抽卡和角色获取动画。
- 完整养成树。
- 装备、词条和强化。
- 剧情、配音和任务系统。
- 多章节地图。
- 自动战斗倍速和跳过。
- 商店和任何付费入口。
- 云存档和多设备同步。

### 明确不做

- 原服务器协议复刻。
- 反作弊绕过或在线作弊。
- 商业发行和公开分发原 IP 素材。

## 9. 成功标准

### 产品成功标准

- 用户能在 3 分钟内从启动进入第一场战斗。
- 一场战斗有明确的开始、过程、胜负和奖励反馈。
- 战斗结果受编队和技能选择影响，而不是纯播放动画。
- 连续完成 3 场战斗不需要重启应用。
- 退出并重新进入后，编队和奖励状态不丢失。

### 技术成功标准

- Android ARM64 构建可安装并启动。
- 目标模拟器上无持续异常日志和阻塞性报错。
- 战斗核心可脱离 UI 运行确定性测试。
- 新增一个角色或关卡不需要修改战斗核心代码。
- 存档包含版本号，升级后可以迁移或安全重置。
- 首次可玩版本的安装包和内存占用保持在目标设备可接受范围内。

### 证据成功标准

- 原游戏的关键判断都有截图、视频、日志或元数据支持。
- 分析产物带来源、时间、设备和文件哈希。
- 设计文档明确区分“原游戏行为”“我们的取舍”和“未知事项”。

## 10. 约束

- 开发时间受限，不能按完整商业项目估算。
- 3D 角色、动画、特效和场景制作成本高。
- 原游戏资源不可直接作为最终发布资产。
- MuMu 的 ADB 端口和图形兼容性可能因版本变化。
- 商业手游可能使用热更新、资源加密、split APK 或服务端逻辑。
- Android 设备性能和屏幕比例差异会影响 UI 和战斗镜头。

## 11. 主要风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 游戏实际为强联网或服务端驱动 | 无法完整离线复刻 | 只复刻客户端可见循环，自建本地数据层 |
| 资源加密或远程下载 | 无法直接读取角色和关卡数据 | 以画面和日志反推，使用自制资产 |
| 战斗类型判断错误 | 架构返工 | 先侦察再冻结战斗模型，核心与表现分层 |
| 3D 美术产能不足 | 原型缺乏吸引力 | 使用占位模型、统一材质、少量高质量技能特效 |
| Android 性能不足 | 帧率和发热不可接受 | 控制角色数量、材质、后处理和同屏特效 |
| 范围膨胀 | 长期没有可玩版本 | 以纵向切片为唯一 P1 目标，其他需求进入 backlog |
| 版权和资产混用 | 无法安全分享 | 原资源只存于 analysis，final 构建使用独立资产 |

## 12. 关键决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 游戏引擎 | Unity 6 LTS | Android 3D、角色动画、UI、粒子和构建链路成熟 |
| 分析工具 | ADB + REA + JADX | 覆盖设备、截图、日志、APK、IL2CPP 和原生库 |
| 首版形态 | 纵向切片 | 先验证核心体验，避免内容先行 |
| 数据方案 | 本地 ScriptableObject 或 JSON 配置 | 可快速迭代，后续可迁移到更复杂的内容管线 |
| 存档方案 | 本地版本化 JSON | 易调试、可迁移、便于测试 |
| 资产策略 | 占位资产逐步替换 | 降低早期美术成本 |

## 13. 待确认问题

1. 游戏的真实包名、版本号和引擎类型是什么。
2. 战斗是自动、回合制、半即时还是其他模式。
3. 一局战斗同时出现多少角色和敌人。
4. 玩家在战斗中的操作有哪些。
5. 角色成长和编队是否影响战斗数值。
6. 游戏是否必须联网才能进入核心关卡。
7. 资源是否存储在 APK、OBB 还是远程下载目录。
8. 哪一些界面构成最小可玩闭环。
9. 目标设备分辨率和性能下限是什么。
10. 首版是否保留角色收集界面，还是直接提供固定角色。

## 14. 当前阶段结论

项目已经完成立项和目录建立，环境仍在准备中。下一步不是创建大量玩法代码，而是完成 ADB 连接、识别游戏包、采集首批证据并确认引擎。只有核心循环被证据确认后，才冻结第一版纵向切片范围。
