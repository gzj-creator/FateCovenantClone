# 升级、功能开放、活动开放与活动运营规则（2026-11-12）

配套 `full-service-design-20261112.md`，修复其中 F1–F8、A1–A8。标记含义：

- **【表】** 本次从已加载的客户端表实测得到（脚本 `.tmp/design-probe/probe-rules.mjs`）。
- **【定】** 本设计的决定，原服是否相同未证实。
- **【证】** 需取证，取证前按写明的保守行为处理。

## 1. 统一时间基准

所有规则共用，替换现有散落在 30 多个文件里的 +3h / +8h 常量。

| 概念 | 定义 |
| --- | --- |
| 区服时区 | 每个区服一项配置，默认 `+08:00`【定】 |
| 自然日 | 区服时区 00:00 起 |
| 业务日 | 区服时区 05:00 起，日常重置、任务、签到、限购均以此为界【定，逐模块核对见 §8】 |
| 服务器日 | 开服所在业务日为第 1 天，之后每过一个业务日加 1。与开服的具体时刻无关 |
| 周 | 周一 05:00 起【证】 |

只提供四个函数：`naturalDay(t)`、`gameDay(t)`、`serverDay(t)`、`gameWeek(t)`。业务代码不得再自带偏移常量；启动时扫描源码，发现裸写的 `10800/18000/28800` 即测试失败。

## 2. 升级规则

### 2.1 数据

【表】`RoleLevel` 300 行，字段 `reach_exp`（本级升下一级所需）、`mission_award_num`（主线通关经验）、`reward_id/reward_count`（等级奖励）、`attr`、`role_attr`（等级属性）。`RoleLevelSetting.max_level = 300`。

### 2.2 经验入口

所有经验只走一个函数 `addRoleExp(role, amount, source)`，主线结算、任务、道具、活动奖励、邮件、GM 全部调用它。

```
exp += amount
while level < maxLevel and exp >= reach_exp[level]:
    exp -= reach_exp[level]; level += 1; 记录跨过的等级
满级后 exp 封顶为 reach_exp[maxLevel]，多余丢弃【定】
```

`exp` 语义固定为“当前等级内的经验”。现有“奖励发经验只累加不升级”的路径删除。

### 2.3 升级后动作

每跨过一级按序执行，与触发升级的业务在同一事务内：

1. 写入等级。
2. 重算功能开放（§3.3），新开的功能写入位图。
3. 等级属性（`attr`/`role_attr`）进入属性管线，战力缓存失效。
4. 发事件 `role.levelUp{from,to}`：等级榜、冲级活动、成长目标、任务统计订阅。
5. 重算依赖等级的活动可见性（§4.2 第 6 步）。

事务提交后推送：资源变化（沿用现有 `[level, exp]` 附加字段）、功能开放变更、战力变更。推送的 S2C 类型见【证】E9-4。

### 2.4 等级奖励

沿用现有领取命令：一次领取“已领等级+1 … 当前等级”的全部奖励，记录已领到的等级。不自动发放【定，与现有实现一致】。

### 2.5 其他

- 体力上限随等级：现有按读取时计算，保持。升级是否赠送体力【证】，取证前不赠。
- GM 设置等级：升级走同一流程逐级执行；降级只改等级和经验，不回收已开功能和已领奖励。
- 存量角色：登录时做一次规范化——经验溢出则补升级，再重算功能开放。

## 3. 功能开放规则

### 3.1 现状约束

- 功能 id = 目标类型 ×1000 + 序号。目标 1（1001–1999）由客户端判定条件后发 7000 申请；目标 2 由服务端开启。
- 【表】抓包存档中目标 1 已开 134 位、目标 2 已开 5 位。
- 服务端当前没有任何开放条件表。客户端的功能开放表未导出【证 E9-1】。

### 3.2 规则模型

从客户端功能开放表生成只读资产 `fun-open-rules.json`：

```
{ funId, target, conditions: [{type, args}], group }
```

条件类型（同一功能内全部满足才开；表里若有“任一满足”分组则按分组）：

| type | 含义 |
| --- | --- |
| `role_level` | 团长等级 ≥ N |
| `mission` | 主线通关到指定关卡 |
| `server_day` | 服务器日 ≥ N |
| `guide` | 指定引导步骤完成 |
| `fun_open` | 依赖的另一功能已开 |
| `hero` | 拥有指定英雄 / 英雄数 / 星级 |
| `create_day` | 创角天数 ≥ N |

表中出现以上之外的条件类型时，该功能判为“未开”并记日志，不猜语义。

### 3.3 判定与触发

`evaluateFunOpen(role) → 应开集合`，纯函数。触发点：创角、登录、升级、主线通关、引导推进、业务日切换、运营覆盖变更。

- **单调**：已开的功能不因条件回退而关闭。
- **目标 2**：触发时由服务端直接写入位图并推送。
- **目标 1（7000 申请）**：逐个 id 用同一规则复核。满足则置位；不满足则忽略该 id 并记 `fun_open_denied`。回包始终返回服务端的权威位图，不向客户端报错【定】。
- 取证完成前的过渡：7000 维持现状但记录全部申请，用来对照规则表；新号位图从空开始。

### 3.4 命令门禁

命令注册表为每条命令声明 `requires: funId`（映射来源【证 E9-2】）。

| 情况 | 行为 |
| --- | --- |
| 写命令，功能未开 | 拒绝，错误码取客户端错误表中“功能未开启”项【证 E9-5】，未确认前用 309 |
| 读命令，功能未开 | 返回空状态，不报错 |
| 登录数据 | 未开功能的模块下发空态，保证登录不因此失败 |
| 未声明 `requires` 的命令 | 启动时列入报告，逐步补齐；不阻塞 |

### 3.5 新号与存量

- 新号：位图清空，创角时按规则判定一次。
- 存量角色：按规则重算，与“该功能下已有进度”的集合取并集，避免已有数据的功能被关掉。
- 测试策略（强制开启 1039/1322/1348/1537）从启动逻辑移除，改为 §3.6 的运营覆盖，按区服对全部角色生效。

### 3.6 运营覆盖

`fun_open_override(server_id, fun_id, mode, reason, operator, at)`：

- `force_open`：对该区服全部角色开放，写入各角色位图（登录或在线推送时生效）。
- `force_close`：紧急关闭。不改角色位图，只在下发和门禁时屏蔽；解除后恢复。
- 所有覆盖进审计日志。

## 4. 活动开放规则

### 4.1 表内事实【表】

| 表 | 行数 | 时间类型分布 | 其他 |
| --- | ---: | --- | --- |
| ActFrameAct | 884 | `time_type`：2×488、1×379、3×10、4×3、5×3、0×1 | `world_time>0` 488 行，`refer_day>0` 402 行，`time_fun=461` 3 行，`asserts` 仅 1 行非空 |
| Activity | 1109 | `time_type`：0×666、1×395、2×32、3×16 | `server_day>0` 714，`world_time>0` 395，`join_server_day>0` 215，`discard_time>0` 152，`world_limit_state=3` 78，`server_limited_type=1` 15 |

Activity 的状态序列：`state` 取值 `[10,50]`×120、`[50]`×32、`[50,90]`×23、`[50,60,90]`×13、`[50,60]`×13，配套 `state_end_day`（如 `[1,5]`）给出每个状态的持续天数。

由行数对应可知：ActFrameAct `time_type=2` 是世界时间、`1` 是开服相对日；Activity `time_type=1` 是世界时间、`0` 是开服相对日。其余取值含义【证 E10-1】。

### 4.2 判定顺序

对每个活动按序判定，前一步不通过即结束：

| 步 | 判定 | 规则 |
| --- | --- | --- |
| 1 | 运营覆盖 | `pause`/`force_close` → 关；`force_open` → 用覆盖窗口，跳到第 5 步 |
| 2 | 废弃 | `discard_time>0` 且当前时间已过 → 关。按绝对时间，不随开服平移【定，与现有审计口径一致】 |
| 3 | 区服资格 | `join_server_day`（服务器日下限）、`server_day_limit`（服务器日上限）、`server_mini/max_open_limited`（开服时间范围）。`server_limited_type=1`、`world_limit_state=3`【证 E10-2】，取证前这 93 行判关 |
| 4 | 时间窗 | 开服相对：第 N 服务器日 + 起始偏移，持续 `duration_day`，至 `end_time`。世界时间：按“目标服开服 − 参考服开服”平移。其余 `time_type` 与 `time_fun=461`【证】，取证前判关 |
| 5 | 状态 | 按 `state` 与 `state_end_day` 从窗口起点依次推算当前状态（§4.3）。ActFrameAct 用 `stage`/`stage_end_time`/`stage_duration_day` 同理 |
| 6 | 玩家条件 | 活动入口对应的功能（`jump_func`/`func`）对该角色已开；`asserts` 条件满足；运营覆盖里的等级/创角天数条件满足。不满足则对该角色不可见 |
| 7 | 父子 | 子活动（礼包商城、兑换商店等）继承父活动的窗口和状态，自身不单独判定时间 |

前 5 步的结果按区服缓存；第 6 步按角色计算。

删除两条现有行为：不再读取抓包存档的 `cur_state_id` 决定开关；表里没有的活动一律不开。

### 4.3 状态机

| 状态 | 客户端值 | 可见 | 可操作 | 可领奖 |
| --- | --- | :-: | :-: | :-: |
| 未开始 | — | 否 | 否 | 否 |
| 预告 | 10 | 是 | 否 | 否 |
| 进行 | 50 | 是 | 是 | 是 |
| 领奖期 | 60【证 E10-3】 | 是 | 否 | 是 |
| 展示期 | 90【证 E10-3】 | 是 | 否 | 否 |
| 关闭 | — | 否 | 否 | 否 |

离开“进行”时执行一次结算（§5.5）。60/90 的语义取证前，含这两个状态的 49 行在“进行”结束后直接关闭，未领奖励走邮件补发。

所有活动命令统一调用 `activityGate(actId, 需求)`，需求为 `read / operate / claim`，按上表放行；不通过统一返回“活动未开放”。

### 4.4 期数与个人状态

- 活动实例键 `(act_id, period_no)`；循环活动每个周期一个期号。
- 个人状态键 `(role_id, act_id, period_no)`。进入新期时，期内计数、领取位、限购清零；跨期累计项由各家族显式声明，默认不保留。
- 首次访问新期时惰性创建个人状态，不依赖登录。

### 4.5 状态切换与在线同步

调度器每分钟检查一次，启动时补跑停机期间错过的切换。每次切换在一个事务内：更新实例状态 → 执行结算 → 写待发邮件 → 发 `activity.stageChanged`。提交后向在线角色推送活动列表与阶段时间的变更（推送类型【证 E9-4】；取证前在客户端下次请求活动列表时返回最新状态）。

业务日切换时同样由调度器触发：重算服务器日、重算全部活动、向在线角色推送。

## 5. 活动运营

### 5.1 配置分层

| 层 | 内容 | 修改方式 |
| --- | --- | --- |
| L0 客户端表 | 活动定义、奖励、默认时间 | 只随客户端版本更新，带版本号与哈希 |
| L1 区服日历 | 开服时间、参考服开服时间、时区、日切时点 | 开服时确定，之后只读 |
| L2 运营覆盖 | 单活动的改期、延长、提前结束、暂停、强开、玩家条件 | 管理端，实时生效 |
| L3 紧急开关 | 按活动家族或功能一键关闭 | 管理端，实时生效 |

**客户端一致性约束**：客户端会用自己的表计算活动时间，服务端下发与之矛盾的时间会报“时间配置错误”。因此 L2 覆盖只通过客户端认可的通道表达：登录模块 92 的自定义窗口列表与暂停列表、模块 183 的阶段时间。哪些家族认自定义窗口【证 E10-4】；不认的家族只允许“暂停”和“提前结束”，不允许改期。

### 5.2 覆盖项

`activity_override(server_id, act_id, kind, start_at, end_at, conditions, reason, operator, at, revoked_at)`

| kind | 效果 | 限制 |
| --- | --- | --- |
| `shift` | 整体平移窗口 | 仅未开始的活动 |
| `extend` | 延长结束时间 | 仅进行中；期号不变 |
| `close_early` | 立即进入结算 | 不可撤销，需二次确认 |
| `pause` / `resume` | 暂停期间不可见不可操作，个人状态保留 | 暂停时长不自动顺延，顺延需另加 `extend` |
| `force_open` | 按给定窗口开放一个表内活动 | 必须指定结束时间；该活动的表资产必须已就绪 |
| `condition` | 增加等级或创角天数门槛 | 只能加严，不能放宽表内条件 |

奖励内容、概率、价格不提供覆盖，只能随 L0 表变更【定】。

### 5.3 操作流程

每项变更固定四步：

1. **预演**：输出变更前后对比——受影响的活动、状态变化时刻、在线人数、已参与人数、与客户端表的一致性检查结果。
2. **确认**：`close_early`、`force_open`、紧急开关需要二次确认并填写原因。
3. **生效**：写覆盖表，下一次调度检查时应用并推送。
4. **留痕**：写审计日志（操作人、时间、前后值、原因）。

### 5.4 新活动上线检查

| 项 | 标准 |
| --- | --- |
| 表资产 | 已导出并通过行数与引用校验 |
| 家族模块 | 登录数据、全部命令、事件订阅、结算四个接口齐备 |
| 奖池与奖励 | 非空；引用的物品、英雄存在 |
| 依赖功能 | 入口功能 id 已有开放规则 |
| 排期预演 | 在目标区服的开服日下，窗口与状态符合预期 |
| 测试 | 组件、临时 TCP 通过；含开始前、开始瞬间、结束瞬间、结束后四个时点 |
| 验收 | APK 请求与用户视觉确认后才标记“可运营” |

缺任一项，活动保持关闭，不进入玩家可见列表。

### 5.5 结算

离开“进行”状态时按序执行，每步以 `(act_id, period_no, role_id, step)` 为幂等键：

1. 冻结榜单，写入快照。
2. 按榜单与档位计算奖励，写入待发邮件。
3. 未领取的已达成奖励转邮件补发（家族可声明不补发）。
4. 活动专属货币：有兑换商店的保留到展示期结束再清；没有的立即清零【证 E10-5】。
5. 个人状态归档。

结算前自动备份数据库。结算失败不推进状态，进入告警，可在管理端重试。

### 5.6 补偿与事故

| 场景 | 处理 |
| --- | --- |
| 活动出错需下线 | L3 紧急开关关闭 → 修复 → 解除；按停用时长加 `extend` |
| 奖励发错 | 全服或指定名单邮件补发；多发不回收，记录在案 |
| 结算错误 | 用结算前备份核对差额，差额走邮件；不回滚数据库 |
| 停机维护 | 维护模式挡新登录；恢复后调度器补跑；跨越结束时刻的活动正常结算 |

### 5.7 开新服

1. 从模板生成区服日历：开服时间、时区、日切时点；参考服开服时间沿用。
2. 生成未来 30 天排期预演，人工确认开服首周活动。
3. 跑排期审计，零错误才允许启动。
4. 开服后前 7 天每天业务日切换后核对一次“实际开放列表”与预演是否一致。

### 5.8 监控

| 指标 | 告警条件 |
| --- | --- |
| 活动状态切换 | 到期 5 分钟未切换 |
| 结算任务 | 失败或超时 |
| 开放活动内的命令拒绝 | 同一命令 10 分钟内拒绝超过阈值 |
| 客户端时间配置错误 | 日志出现即告警 |
| 奖励产出 | 单活动单日钻石、招募券产出超过预设上限 |
| 功能开放拒绝 | `fun_open_denied` 持续出现（规则表与客户端不一致） |
| 登录 | 登录数据生成失败 |

### 5.9 权限

管理端分三级：只读、运营（L2 覆盖、邮件、公告）、管理员（L3 开关、强开、GM 发物品、封禁）。所有写操作留审计。
