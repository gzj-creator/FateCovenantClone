# 共享缺口与先行任务

这七项不适合仅按未路由命令统计：有些使用已经存在的命令，有些尚未恢复数字命令。模块任务的依赖指向本文件。主线战斗和大量养成、充值服务已经存在，本轮实施应补齐集成，而不是重新造一套状态。

## CORE-BATTLE：战斗效果、特殊机制与客户端报告

优先级 P1。建议指定一个共享执行器负责人，先交付接口，再由各英雄/副本负责人使用。此任务可按 A/B/C 分步派发，不能多人同时无协调改同一个执行器。

**当前事实**

- `battle-engine.mjs` 已按英雄 `role` 读取技能；普攻、部分终结技及被动/精通的效果和触发器已经在战斗中执行。
- DoT/HoT、伤害、治疗、护盾、能量、部分属性和状态、种子随机、触发次数与生命周期已有实现，不能再次作为“完全没有”开发。
- 部分终结技描述不足，仍使用职业行为兜底；部分技能只是描述推导出的近似。最新边界见 [技能战斗接入记录](../../../agent/workflow/skill-system-validation/battle-integration-20261106.md)。
- 当前还有 75 条技能引用的 source 为 project-fallback；普通攻击和伤害/能量等原始公式的精度仍需对照配置恢复，不能因可执行而认定原规则已经还原。
- `protection/invulnerable/strengthened/frightened/chain/pursuit` 的完整战斗语义，最大生命、命中/闪避、状态命中/抵抗、反弹等公式仍未闭合。类型常量存在不等于结算公式已执行。
- 服务端没有发送 `pb_fat_buff_change`（proto 103）；缺少语义到真实 `FightTable.Buff.tid` 的映射，BUFF 图标、状态提示和消失回放仍缺。

**实施范围**

| 子任务 | 具体产出 |
| --- | --- |
| CORE-BATTLE-A：通用效果 | 逐项补齐上面的状态/属性结算，以及吸血按实际伤害、下一次攻击/终结技/受击消费、按伤害转盾/治疗、队友行动和跨单位触发。已有选择器包含前排友军/前排最高攻击，不重复补旧审计已修项。 |
| CORE-BATTLE-B：专有机制 | 依据逐英雄清单补天极值及独立消耗/恢复、超凡生命、召唤与替死、领域、专有层数、追击/协同/复制、额外行动、护盾按比例摧毁及伤害上限。先定义明确的公共状态/事件接口，按实际描述覆盖，不能把天极值直接当普通能量。 |
| CORE-BATTLE-C：报告 | 取得真实 BUFF tid 后补 103 状态变化及对应生命周期回放；统一实际模拟结果、伤害/治疗/护盾/能量/死亡/复活/召唤事件与客户端报告。不得编造 tid。 |

源码入口：`personal-server/game/battle-engine.mjs`、`game/effects/*`、`game/mission-fight-service.mjs`、`config/skill-database.json`。继续使用现有战斗内核和协议结构。

验收：同一输入和种子重复模拟一致；每种新增语义有实际战果断言；触发不会自递归或每回合永久叠加；报告反解与最终 HP/护盾/能量/生死一致。通过现有战斗与技能回归，再记录真实客户端视觉待验项。

## CORE-ATTR：养成属性、敌方数值与战力统一接入

优先级 P1。它是大量“养成按钮能点，但养成没有完整进入战斗”的共同缺口。

**当前事实**

`mission-fight-service.mjs` 的玩家 HP 仍用 `1000 + level * 100 + quality * 10`；攻防速度按职业比例生成。敌人等级参考己方最高等级、HP 再乘本地系数。战力用 HP 汇总。普通装备、团长装备、圣器、Relic、幻武、图鉴、训练、法阵、星魂卷轴、命运/阵营等持久状态尚未统一汇入真实配置属性公式。

**实施步骤**

1. 建立统一服务端属性组装入口，明确基础属性、固定值/百分比加成、最终倍率、取整和上下限的配置依据。
2. 接入英雄等级、星级、突破、品质及已实现装备/图鉴/好感/法阵/符文等状态。后续未实现的养成系统通过同一接口扩展，不各自计算战斗属性。
3. 使用关卡/NPC 的等级、成长、队伍和波次配置，补敌方强度。不能长期以玩家等级缩放代替关卡实际配置。
4. 统一属性查询、战力刷新、阵容战力和战斗输入；保留输入来源以便排查某一项加成。
5. 未取证的公式单列，保留明确标识的兼容行为；不能把项目估算说成原游戏公式恢复。

验收：同一存档的属性查询、战力和战斗取值一致；单独穿脱/升级/升星某项时，只有配置规定的属性改变；重登和 SQLite 重开后数值一致；旧存档迁移不覆盖现有养成。

## CORE-SKILL-GATES：技能等级、解锁条件与实际技能选择

优先级 P1。依赖 CORE-ATTR 的战斗输入约定，可与 CORE-BATTLE-A 协调推进。

**当前事实**

`getHeroSkills` 按英雄返回整份技能列表，`registerPassiveTriggers` 注册其中 Passive/Mastery。主线传入模拟的单位没有完整技能等级、星级/觉醒解锁及已选技能状态。不能把“技能库有定义”当作“该角色当前都已解锁且数值正确”。

实施：从权威英雄状态和配置筛选可用技能及等级；区分普攻、绝招、终结技、天极技、精通、稀有/升级替换技能；对应等级/星级/突破/品质/选择条件驱动技能升级与替换。接入 `HERO-MASTERY` 等后续养成，避免所有精通同时默认生效。

验收：同一英雄不同养成阶段拥有不同且正确的可用技能；未解锁技能不触发；升级后的倍率和触发条件进入真实模拟；已配置的替换技能不会与旧版本重复执行。

## CORE-EVENTS：活动生命周期、任务统计与周期结算

优先级 P1。日周任务、限时活动、全服进度、排行榜奖励共同依赖。

**已有能力**

日历支持 `schedule/all-open`、开服日和时间窗口；部分活动已校验领奖窗口、重置、购买与领取防重。`all-open` 是用户测试策略，不是尚未实现正式日历。

**剩余实施**

1. 补 `53001/53002` 的真实状态/阶段推进和 `53006` 活动列表数据；建立新活动初始数据、预告/开启/结束/展示/结算的配置驱动生命周期。
2. 统一活动 ID、业务版本、角色、周期的作用域；切期只重置当期，保留已定义的跨期累计。保持 module 92/183 和各玩法模块一致。
3. 以服务端实际行为产生任务进度事件：战斗、招募、养成、消耗、登录、购买、助力等。补日常/周常、活动任务及 `9010` 尚未覆盖的进度函数，不接受客户端自报完成。
4. 全服/公会进度由真实持久数据聚合；单人私服也应从该角色行为计算，不能固定“全服已完成”。
5. 补跨日/周/赛季重置、活动结束结算、奖励邮件/补发、重启补跑和防重。排行榜实际排序由 `BATTLE-RANK` 负责，生命周期任务负责触发并记录结算。

验收：开始前、开始瞬间、结束瞬间和结束后行为正确；服务器日与现有模块的各自已证实重置规则一致；离线跨期/重启不会重复发奖或把历史消费重新计入新期；同一事件不会多计，失败事务不产生进度。
