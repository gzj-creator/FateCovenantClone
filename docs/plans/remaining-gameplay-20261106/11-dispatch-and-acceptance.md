# 派发顺序、任务边界与验收

本目录是实施待办，不是已完成清单。每次只领取明确 ID；分区文档中每个二级小节是一张模块任务卡，`SKILL-英雄 ID` 是英雄精度任务，`CORE-*` 是共享任务。

## 建议实施顺序

| 批次 | 推荐任务 | 交付后解锁的工作 |
| --- | --- | --- |
| A：公共能力和日常闭环 | CORE-ATTR、CORE-SKILL-GATES、CORE-BATTLE-A/C、CORE-EVENTS；ITEM-ITEM、ITEM-SHOP、ITEM-EVERYTASK、ITEM-COMMONTASK、ITEM-MISSION、HERO-LINEUP | 养成能进入战斗、任务可完成、物品/商店有真实状态；活动使用统一生命周期。 |
| B：基础玩法与证据 | BATTLE-ELITEMISSION、BATTLE-PEAKTOWER、BATTLE-GENERALDUNGEON、BATTLE-RANK；HERO-HERO、HERO-MASTERY；SOC-FRIEND、SOC-MSG、SOC-CHAT、SOC-GUILD；CORE-DRAW-POOLS；时空神殿/船舱取证 | 精英/爬塔/地牢、真实排行榜、好友公会、可用生产奖池。证据工作可与 A 并行。 |
| C：后期养成与特殊战斗 | EQUIP-ARTIFACT、EQUIP-RELIC、EQUIP-LEADEREQUIP、EQUIP-PET、EQUIP-TREASURE、EQUIP-ELVES 及其余装备模块；CORE-BATTLE-B；SKILL-* | 后期养成与天极/领域/召唤/专有机制，供高阶副本和活动使用。 |
| D：竞技与公会活动 | 01-battle.md 的其余竞技/匹配/观战/竞猜；05-social-guild.md 的公会试炼、探索、战、国战、BOSS、竞速、远征和拍卖 | 多玩家/多队/跨服逻辑与周期结算。单机部署也从真实本地角色数据计算。 |
| E：活动优先补现有半成品 | PLAY-FISHINGACT、PLAY-HELPUPACT、PLAY-PETACTIVITY；DRAW-HUNDREDDRAWACT、DRAW-ARTIFACTDRAWACT、DRAW-DEMIGODACT、DRAW-FANTASYEQUIPACT、DRAW-WISHTREE；PAY-GROUPBUYACT、PAY-DRAGONLANDACT | 优先消除当前可见活动的空数据、拒绝领奖、缺战斗来源等问题。其证据与公共能力准备可提前进行。 |
| F：全部剩余活动与外围 | 06–09 分区剩余任务，及 10 分区玩家相关功能 | 补全抽取、节日、小游戏、家园、福利/礼包/基金/通行证等；辅助命令单列后置。 |

批次是依赖建议，不是要求严格串行。没有战斗依赖的签到、礼包和小游戏，在 CORE-EVENTS/资源约定就绪后可以提前派发。缺配置/命令映射的任务先做现有证据核对和可证部分，将缺口具体交给总控，不反复询问是否继续。

## 共用文件与独立 worktree

- 总控统一维护 `gateway.mjs` 路由接入、`game-store.mjs` 的 schema 迁移、配置读取器、登录模块容器、公共资源处理器与任务索引；普通模块 agent 先实现独立服务与接入补丁。
- `battle-engine.mjs`、`game/effects/*` 由 CORE-BATTLE 负责人协调。逐英雄 agent 只修改分配英雄的数据、必要测试和对应记录；按现有脚本应用技能补丁。
- 不同 agent 使用各自分支/worktree；开始和合并前核对最新主线，不覆盖工作区已有用户改动和其他 agent 文件。
- 一个活动通常跨登录、商城/礼包、任务、战斗、奖励和周期。任务负责人负责闭环，跨模块改动以依赖接口协调；不能只说“接口已加”而把剩余业务留给不明确的后续任务。
- 静态模块是协议编码分组，不一定是一项独立玩法。多队竞技、国战等大模块应在原任务下继续按状态/子系统拆分，由同一负责人集成，避免共同资源各实现一遍。

## 每张任务卡的实施步骤

1. **核对最新状态**：读取当前 AGENTS.md、任务卡、inventory.json、对应服务及工作记录。2026-11-06 后若已新增实现，调整剩余范围并保留证据；不要复写可用功能。
2. **关闭协议与规则缺口**：从静态目录按 type/名称定位 request/response、ETF/PB 编码、Manager 调用、表/消耗/奖励、登录槽位与推送。inventory.json 用 staticRecordId 引用原证据，不重复复制大报告。响应 schema 为“—”只是尚未恢复，不意味着应该回空包。
3. **写明实现设计**：列权威状态、实体关系、活动/版本/周期作用域、资格/解锁、失败码、资源、奖励、防重、刷新/结算与回包。明确配置事实和推断。部分功能不在当前版本时，给出不可达证据，不伪造玩法。
4. **完成真实业务**：复用现有 codec、资源、钱包、库存、邮件和事务。调用 helper 必须接入生产请求/定时/事件路径；回包、登录与推送读取同一权威状态。
5. **验证完整闭环**：按下文服务、临时 TCP、SQLite 重开和异常事务要求验证。新增资产收纳进 personal-server/assets，保持个人服务器独立交付。
6. **写交付记录**：输出 `agent/workflow/gameplay-completion/<任务 ID>/implementation.md`，保存配置依据、修改、复现命令、证据、验收层级与具体剩余问题；更新本计划任务状态。实际运行证据放 analysis，敏感数据保持 local-only。

## 共同验收标准

| 层级 | 要求 |
| --- | --- |
| 业务 | 正常操作、合法边界、资源不足、未解锁、非法 ID、重复/过期操作有正确业务结果。不能统一回成功、固定胜利、空榜或固定全服进度。 |
| 事务与持久化 | 消耗、库存/属性、奖励、任务进度、领取位/订单和回包编码在一致事务中提交；编码或 SQLite 写入失败整体回滚。重开数据库后状态与防重仍有效。 |
| 临时 TCP | 使用现有握手/登录测试路径，通过实际数字 type 解码请求与响应；验证登录模块、资源变化、推送字段/顺序。只直测 service/helper 不能认定网关接通。 |
| 时间与活动 | 启停窗口、每日/周/赛季重置、活动版本切换、离线跨期、服务重启补跑与最终结算按配置实现；旧活动状态不污染新活动。 |
| 业务事件来源 | 奖励资格、挑战伤害/胜负、招募次数、助力和全服统计来自真实服务端行为。测试手工写计数不能代替生产事件接线。 |
| 回归 | 执行与改动相关的现有测试。合并时由总控执行 personal-server 的 `npm test`；新增运行资产/部署依赖时执行 `npm run test:deployment`。不反复扩测已通过且未再变更的部分。 |
| APK/UI | 单独记录真实隔离客户端操作与视觉结果；组件/TCP 通过不能冒充实际可玩验收。当前任务阶段不启停实时服务、不操作模拟器/运行数据库。后续由用户安排该层验收。 |

如用户后续明确授权设备或部署验收，以当时授权为准，普通已授权步骤无需重复确认。只操作隔离 `com.jzyx.ps` 和指定设备 `127.0.0.1:16448`，不连接原游戏服务器、不操作原包。若确需修改 APK，遵循 AGENTS.md 的验收后可用快照与 apk/README.md 记录规则；纯服务端改动不制造新 APK 快照。

## 哪些属于待实现，哪些只需要验收

- **待实现**：未路由、明确拒绝、空结构/固定值、缺少生产配置、缺少事件调用方、养成未进入战斗和特殊规则近似。
- **已实现待复核**：存在真实处理路径但缺完整规则证据。按任务卡的具体限制核查，不能因未做 APK 验收就全部重写。
- **仅待 APK 验收**：服务业务、生产配置、临时 TCP、持久化均已闭合，只缺真实客户端操作。进入验收队列，不继续冒充未实现代码。
- **证据阻塞**：没有命令号、配置或效果定义；写出具体缺失证据和已完成部分。不得猜协议号、编奖励或把未知行为标完成。
- **历史/辅助**：GM、开发登录、埋点/诊断、历史活动声明保留在全集中供核对，不等于当前玩家入口。非目标项应有归类依据，不从原始清单静默删除。

## 交付状态表

总控在 [执行状态表](execution-status.md) 登记负责人、分支、证据和下一依赖。推荐状态：`待领取`、`实施中`、`证据待补`、`服务端完成`、`待 APK 验收`、`APK 验收通过`、`本版本不可达`。只有最后一种有不可达证据时才能从当前版本玩法范围排除；它不能伪装成实现完成。

各阶段分别记录，不以单个 done 覆盖所有层级。任务数量不是完成率；大模块和一条领奖命令工作量不同。
