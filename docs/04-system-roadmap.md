# 完整系统路线与功能验收

> 日期：2026-10-25；状态：开发路线已确定，原游戏未实测规则待确认。
> 用户范围：战斗系统、角色图鉴、角色技能、养成，后续天极角色与法阵；专属武器延期。
> 本文负责后续范围与开发顺序；`03-first-slice-spec.md` 负责首个 3v3 切片。更早文档中的阶段安排冲突时，以本文和用户最新指令为准。

## 1. 交付目标与当前起点

最终体验：查看角色图鉴与技能 → 养成角色 → 调整角色及队伍配置 → 挑战关卡 → 3D 战斗与技能演出 → 结算奖励 → 本地保存 → 再次挑战。后期将已验证的天极角色与法阵接入同一循环。

当前已有原游戏 APK 与运行观察、战斗录像、圣器上阵及星火教学证据。2026-10-25 已补齐 R0 的版本/包清单和工程自动化源码，R1 的程序化 3v3 表现与 RuntimeSmoke 源码，以及 R2 的图鉴、编队、独立关卡页、奖励与存档源码；纯 C# 战斗 37 项断言、游戏逻辑 8 个场景及基于既有 Unity 2022 Player API 的三个运行程序集分开编译已通过。Unity 6 编辑器尚未实际打开工程，Setup 生成场景、Smoke 运行画面、Android 构建及设备验收均无成功证据；当前没有可宣称通过验收的独立 APK。具体状态与续接入口见 [05-development-status.md](05-development-status.md)。

现有内核采用项目自定的速度排序、怒气、选敌、伤害公式和战意规则。这些可支持切片验证，不能当作已恢复的原游戏机制。现有技能实现以伤害、治疗、护盾为主，不视为已经支持完整被动、控制、嘲讽、加攻和后期机制。

设置两个交付节点：

- 首个可玩 APK：3 名可用角色、首批图鉴与技能详情、固定 3v3、1 个关卡、技能表现、编队、结算和本地存档。
- 系统扩展版：图鉴、完整角色技能配置、基础养成、圣器与星火、天极角色、法阵，以及对应的 3D 表现和 Android 验收。角色总数和内容数量随实测及资产产能确定。

建模、动画和特效从切片阶段开始，每扩展一种玩法同步补齐表现。专属武器的独立养成、解锁、词条和专属技能改造延期；角色手持武器的基础模型和攻击动画仍属于角色制作范围。

| 星火 | 阶段/节点、材料、激活与队伍属性 | 岩星 I 与激活已观察；一次点击激活多少节点、叠加规则待确认 | R4 |
| 天极角色 | 图鉴分类、拥有/成长状态、技能差异、编队及完整战斗表现 | 当前仅为用户指定后期范围；不预设是独立角色、进阶形态或稀有度 | R5 |
| 法阵 | 选择/配置、效果说明、生效条件、战斗前后效果与视觉反馈 | 类型、槽位、阵位依赖、资源及释放机制均待成品号核实 | R6 |
| 主流程 | 大厅、关卡、编队、结算、奖励、设置、版本化本地存档 | 采用本地实现；不需要复刻原游戏账号或服务器 | R2、R7 |
| 专属武器 | 仅在待办清单记录与技能的依赖 | 用户明确延期，不占近期功能开发与资产制作额度 | 延期 |

图鉴先支持完整的本地目录结构，再分批加入有技能和资产支撑的角色。图鉴登记、角色可上阵、模型完成、技能完成分别标记，不把有一张卡片视为角色已经可玩。皮肤、好感、羁绊若实测发现，先记录影响；仅直接影响当前战斗验收的部分评估纳入范围。

当前源码登记 6 项角色定义，其中 3 名初始角色已拥有并可上阵，3 名敌方角色作为未拥有图鉴项。已有按名称固定排序、全部/已拥有筛选、属性/技能/获取来源说明和可旋转程序化模型；编队界面只交换 3 名初始角色的站位。独立关卡页已显示固定敌队、胜利奖励和我方队伍，主界面/队伍页先进入该页再挑战。图鉴、队伍及关卡页的实际交互和布局仍待 Unity 验证；正式角色美术、后续角色替换与扩展筛选/排序方式仍未完成。

## 3. 成品号分析计划

用户准备已解锁功能的成品号后，在模拟器内通过正常界面观察。用户自行完成登录即可，不需要把密码写进项目文档。当前不继续依赖新手号逐级解锁来调查后期系统。

| 批次 | 查看对象 | 需要留下的证据及产物 |
| --- | --- | --- |
| A | 角色总览、图鉴、角色详情与完整编队 | 类别/筛选、拥有状态、属性、阵位限制、各成长阶段入口，形成角色字段表 |
| B | 普通角色普攻、主动、被动与技能成长 | 描述原文、等级和阶段、触发条件、目标、效果、持续时间、叠加/驱散规则，形成技能表 |
| C | 固定关卡的普通战斗与技能释放 | 完整录像、阵容/配置快照、行动与触发时间线、状态图标、死亡和结算；至少完成一次可解释的触发链 |
| D | 圣器、星火与普通装备 | 出场配置、属性生效范围、养成前后预览；条件允许时只改一个配置做对照 |
| E | 天极角色 | 普通/天极的关系、可见成长与技能阶段、阵容限制、特写与变身等实际存在的演出；有对照对象才判定差异 |
| F | 法阵 | 管理入口、槽位/阵位、说明和升级预览；同队同关、仅改法阵的对照录像 |

优先选具有代表性的输出、护卫、治疗/辅助，以及实际存在的控制、追击或特殊机制角色；采集规模由账号拥有内容决定。先完成代表角色，再扩大图鉴数据，避免逐个记录全部角色而延误可玩版本。

成品号用于查看和经授权的体验；默认以详情、预览和可恢复配置为主。付费、稀缺材料消耗、不可逆升级或账号绑定操作另行取得具体授权。没有对照条件时，明确记录无法区分的因素，不把多次战斗差异直接归因于法阵或天极属性。

每项机制记录：版本、角色/技能/装备及等级、阵容与关卡、观察步骤、截图/视频、事实、推断、未知、对应实现决策。账号昵称等非必要信息不抄入规格。机制仍不明时，可以保留项目自定配置进行原型验证，并在规格里标明来源。

## 4. 架构与数据约束

沿用现有 Domain / Application / Presentation / Data / Infrastructure 分层，优先扩展现有代码，不先搭无使用场景的通用框架。

| 数据/模块 | 责任 |
| --- | --- |
| CharacterDefinition | 稳定 ID、类别、基础属性、成长引用、技能引用、3D 模型/头像；全局定义不保存玩家进度 |
| CharacterProgress | 拥有状态、等级、已确认的成长阶段、装备引用；以稳定 ID 保存在版本化存档 |
| SkillDefinition / StatusDefinition | 目标、效果、触发、持续时间、叠加与移除规则；首期只支持实际使用的效果 |
| SquadLoadout | 阵位、角色实例、圣器出场配置，后续增加已确认的法阵配置 |
| BattleSnapshot | 开战时解析角色成长与队伍效果，冻结属性、技能版本、配置及种子，避免战斗中养成改变当前结果 |
| BattleSimulator | 调度、效果结算、状态、随机源、胜负；输出事件与最终统计，不依赖 Unity |
| BattlePresenter | 消费事件，处理角色动画、命中点、技能镜头、特效、音效、飘字；不决定数值结果 |
| Catalog / Detail UI | 图鉴与角色详情读取相同定义和玩家进度，技能展示读取战斗使用的配置，避免文案与行为分叉 |
| Save / Rewards | 存档版本迁移、损坏恢复、奖励仅结算一次、配置合法性校验 |

被动和状态的触发顺序必须显式记录；有追击/反击时限制递归触发并记录原因。群体技能、死亡、复活等新效果按证据逐项实现，覆盖实际出现的触发组合。若后期发现无法用现有效果表达的机制，新增局部规则处理器，并保持确定性和事件追踪，不为每名角色复制一套战斗内核。

天极角色与普通角色的身份关系在实测后确定；法阵不提前假定是地面特效、队伍光环或主动技能。现阶段只保留稳定 ID 与战斗快照的扩展空间，不实现空壳系统。

倍速只影响播放速度。切片使用预结算事件播放；若成品号证实存在手动释放，再增加带逻辑时点的指令输入并验证可重放性，不强行沿用开场已算完所有结果的模式。

当前战斗实例 ID 与角色定义 ID 已分离，事件直接输出剩余生命/护盾、护盾吸收、行动者怒气与战意。当前 `GameSession` 将规则版本、双方角色 ID 顺序、种子及战斗票据写入存档；认领奖励时重新模拟该快照，不信任界面传回的结果。当前无养成，尚未冻结成长后的完整数值资产；接入养成时仍须满足上表的完整战斗快照约束。存档已采用带版本和校验和的 `profile.fcsave` 记录格式，非旧方案中的 JSON；已有临时写入、原子替换、备份恢复与未知版本保护，尚无旧版本迁移需求或迁移实现。

## 5. 开发阶段与验收

R 编号是本路线的交付批次，区别于旧实施方案的 M 编号。按依赖推进；成品号取证可以与不依赖其结果的工程开发交错进行。

当前 R0、R1、R2 已有相应源码、独立逻辑验证和 Unity 2022 Player API 兼容编译，仍不能勾选为阶段完成。写入工程配置不代表匹配编辑器已导入，独立 C# 测试或其他 Unity 版本程序集编译通过不代表 Unity 6 编译/运行或 APK 验收通过。RuntimeSmoke 已实现，尚未运行；先补齐现有实现的编辑器与设备证据，再按下表判定阶段。

| 批次 | 交付内容 | 开始条件 | 完成条件 |
| --- | --- | --- | --- |
| R0 工程基线 | 定位或安装 Unity 6 LTS、3D/URP 工程、Boot/Main/Battle、Android IL2CPP ARM64 构建脚本与日志 | 已有工程目录及纯 C# 原型 | 空包在 MuMu 可安装启动，版本固定，无持续应用异常 |
| R1 3D 战斗切片 | 3 名角色、1 关 3v3、普攻与技能、镜头/飘字/受击/死亡、倍速/跳过、胜负展示 | R0；沿用明确标记的原型规则 | 连续 3 场无阻塞；同输入同种子结果一致；数值和画面一致；至少一种完整技能演出 |
| R2 图鉴与本地闭环 | 首批图鉴、已拥有/未拥有、详情及 3D 查看、技能说明、编队、关卡、奖励和存档 | R1；完成角色字段设计 | 修改编队影响战斗；奖励仅入账一次；重启保留角色/编队/资源；损坏存档可恢复；输出首个可玩 APK |
| R3 技能与队伍扩展 | 按成品号校准行动/选敌/状态、补充被动与实际需要的技能效果；支持实测阵容规模 | R2；对应技能/阵容证据可用 | 至少覆盖输出、护卫、治疗/辅助和一种已确认特殊触发；组合可追踪、可复现；详情与行为一致 |
| R4 养成与队伍能力 | 角色等级及已确认成长、普通装备强化/铭刻、圣器、星火；分项交付，优先影响战斗的机制 | R3；每项规则完成观察 | 属性构成可解释；预览与实值一致；资源和成长持久保存；圣器至少一次完整实战释放有证据与实现 |
| R5 天极角色 | 先完成 1 名代表角色的图鉴、成长入口、技能差异、模型/动画/特效和战斗接入，再批量扩展 | R3/R4 中实际需要的依赖就绪；天极身份与技能规则有证据 | 可查看、可编队、可战斗、可保存；阶段切换与技能覆盖正确；原有普通角色无回归 |
| R6 法阵 | 先做 1 套完整法阵的配置、说明、生效与表现，再按不同机制增加 | R3/R4 中实际需要的依赖就绪；法阵规则有证据 | 同队配置前后效果可解释；适用范围和时点正确；切换/卸下无残留，重启配置保留 |
| R7 Android 扩展版验收 | 汇总内容、补齐代表性美术、性能、适配、暂停恢复与回归 | R2 至 R6 纳入版本的内容已完成 | 图鉴→编队→养成→战斗→结算闭环；MuMu 与可用真机验证；记录版本、性能及剩余问题 |

R5 与 R6 的先后可根据成品号暴露的真实依赖调整。若天极技能必须依赖专属武器，先实现不依赖部分，并明确缺口；是否提前纳入那一项专属依赖由用户重新定范围，不能隐式把完整专武系统带回近期工作。

首个 APK 先完成 R0 至 R2，不等待天极、法阵或全角色资料。R3 之后每个批次均保持可运行 APK。完整角色数量、内容扩展工期和最终帧率预算，在首名完整角色与首个设备包有实测成本后再估算，不用原型内核已完成来推断全项目接近完成。

## 6. 模型、动画与特效安排

- R1 先用程序化角色校准站位和镜头，随后同批次完成首名自制角色的建模、材质、绑定、待机、移动、普攻、技能、受击、死亡；确认流程后覆盖其余两名。角色与技能先求完整，再增加数量。
- 当前关节式程序化人物及基础动作只用于工程验证，正式模型、绑定、动画与角色专属特效仍未完成；不能以源码生成了人物形状替代美术验收。
- 每名角色记录模型/材质/动画/头像/技能特效清单和授权来源。原游戏截图、模型及演出仅在 `analysis/` 用于比较。
- 图鉴与战斗复用同一角色定义和基础模型，通过灯光、镜头及表现配置适配展示；避免做出图鉴好看但战斗无法运行的孤立资产。
- 特效分为命中、弹道、范围、状态、角色特写与队伍能力；按实际命中事件同步，控制透明叠层、粒子峰值和屏幕遮挡。天极/法阵只有在对应机制确认后制作专用演出。
- 每批次在竖屏 16:9 至 20:9 检查文字、角色和特效构图；初始目标 60 fps、最低 30 fps，最终以选定设备的测量结果调整预算。

## 7. 验证重点

| 范围 | 必须检查的行为 |
| --- | --- |
| 战斗与技能 | 同种子可复现、目标失效、同速、护盾与伤害顺序、状态过期、触发链、死亡和胜负、已实现特殊效果组合 |
| 播放与操作 | 普速/倍速/跳过结果一致；数字、血条、受击一致；未来手动指令有记录可重放 |
| 图鉴与编队 | 未拥有状态、筛选、详情数值、技能文本、非法/重复阵位、可用角色不足、布局适配 |
| 养成与配置 | 材料不足、达到上限、属性重复计算、卸装/换法阵后的移除、生效范围、重启和存档迁移 |
| 结算与设备 | 重复点击不重复奖励、中断恢复不重结算、连续挑战、暂停恢复、内存/帧率和日志异常 |

测试随风险增加：领域层验证规则与触发组合，编辑器检查事件播放和界面，ADB/设备检查安装与完整闭环。只用画面相似或总战力接近，不能判定机制复刻完成。

## 8. 下一步与延期清单
