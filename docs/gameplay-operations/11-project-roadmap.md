# 11 完整项目规划、工作包与交付门槛

更新：2026-11-14。当前维护范围是 `personal-server/` 与隔离客户端 `com.jzyx.ps`。本文把玩法说明、原始规则目录、历史任务卡和运营执行统一为一份可继续实施的规划；本轮完善文档，业务修复由相应任务另行推进。

## 1. 目标、范围与唯一例外

交付目标是让玩家按原版本的条件获得相同对象、经历相同流程，并在相同的资源、养成、关卡、活动和商业限制下游玩。还原对象包含客户端实际消费的协议、数据、表现和持久化，不能把“有处理函数”作为玩法完成的替代。

**唯一保留的定制游戏系统是代金券。** 代金券的发行、邮件领取、面值与抵扣按本项目方案；钱包提供付款渠道。商品本身的价格、内容、限购、首充、累充、特权和活动资格仍以原版为准。后台加余额只增加付款能力，不产生游戏购买。详细边界见[经济与商业规则](05-economy-and-commerce.md)。

| 范围 | 必须覆盖 | 完成时可以证明什么 |
| --- | --- | --- |
| 基础接入 | 区服、SDK、握手、登录模块、资源版本、断线和重登 | 玩家能进入正确服和自己的角色，必要资源能装载 |
| 完整玩法 | 创角、新手、战斗、关卡、养成、任务、经济、社交、公会、竞技、全部活动族 | 原版可达流程有对应规则、状态、消费、结果与恢复路径 |
| 运营 | 开服、相对/绝对排期、阶段转换、日周重置、结算、订单、邮件、备份与发布 | 按已核规则持续运行，停机与重试不会重复发奖或丢进度 |
| 数据与版本 | 表/脚本/协议来源、ID关系、权威存储、客户端快照、历史迁移 | 每个结果能追到明确版本和真实状态 |
| 验收 | 原版依据、独立预期、组件、TCP、存档、APK、上线后场景 | 能说明某版本具体场景已通过，以及尚未覆盖的分支 |

已取消的 Unity 自制复刻路线不进入当前里程碑；旧 R0–R2、Unity 工具链和占位模型记录只保留历史意义。APK 依项目规则仅保存在本地 `apk/`，不进入 Git 或 Git LFS；修改和可用快照要求见[运营手册](08-operations-runbook.md)。

**文档完成**要求范围清单无遗漏，已知数值原样列出，缺失或冲突明确落到表、字段、消费者和验收用例；读者能复现生成过程并找到依据。**规则恢复完成**还要求缺失的原语义已取得并核对。**玩法完成**还要实现并通过相应场景。三者各自登记，不能因文档已经覆盖某活动名称就把该活动写成可运营。

原版配置、原版脚本、运行观察、当前实现、运营决定分别标记。2026-11-15起执行[最终基线R1](12-final-rule-baseline.md)和[逐任务裁定](rules/final-rule-register.md)，撤回旧【定】设计中未取证且与R1冲突的选择。原特殊时钟优先，其余默认05:00；未证回收的旧币留账冻结；不编自动补邮件；正式world_time不按新服平移。这些是明确执行决定，身份仍分别标原证或复刻推定。

## 4. 依赖与实施顺序

最先统一的是证据、资源事务、身份作用域、时间和持久化。以它们为基础恢复属性/技能/固定敌阵，才能验证养成、主线、PVP和活动战斗。奖池、商品和任务共同依赖资源与事件；活动上线还依赖期号、资格与结算。运营基础贯穿全过程，不能等所有玩法写完再补备份和订单账本。

| 阶段 | 主要工作包 | 进入条件 | 退出时必须交付 |
| --- | --- | --- | --- |
| M0 文档与版本基线 | WP01及全部规则卡目录 | 明确原客户端版本、本服配置和唯一代金券例外 | 全领域目录、逐表事实、消费者/缺口、配置哈希、重建命令、旧文档冲突索引；只代表文档基线成立 |
| M1 新号与共享业务基础 | WP02、WP03、WP04、WP10、WP19基础 | M0对应规则已核，测试存档可隔离创建 | 全新A/B账号隔离；正常创角、Guide奖励/上阵、首章/2-1、失败与重登；资源/订单原子性、必要结构模块和恢复证据 |
| M2 战斗与完整养成依据 | WP05、WP06、WP08、WP09、WP07主线 | M1；相应NPC、技能、属性链有可独立核对数据 | 固定敌阵不随玩家变化；玩家技能门槛、数值通道、动作/状态与胜负原规则闭合；面板/战报/重登一致 |
| M3 常驻经济与商业 | WP10、WP11、WP12、WP13基础 | M1；对应奖池、商品与时间规则已核 | 每类任务/商店/招募/付费完整循环，已售罄与重登正确；累计资格由真实事件驱动；周期状态与订单账本对账 |
| M4 全PVE/PVP及社交公会 | WP07、WP17、WP18 | M2；多账号、共享实例、快照/调度基础具备 | 各模式独立场景、多人身份/并发、真实排名、赛程冻结/发奖、跨服隔离；不依赖捕获账号名册填榜 |
| M5 全活动族与长周期 | WP13、WP14、WP15、WP16 | 该族依赖的M2/M3/M4分支已通过 | 首期/后续期、全部阶段、边界、临时停服/补跑、累计/限购/货币/未领处理；对应APK操作与30/90天排期核对 |
| M6 发布与持续运营验收 | WP19、WP20 | 目标发布包含的场景均已验收，发布阻断清零 | 具体commit/release/数据目录/备份/包哈希、上线后同场景验证、跨日/周/期巡检与事故恢复演练 |

阶段可按规则明确的活动族滚动推进，不能因为后期技能尚缺就阻止已经证实的签到文档完成；同样不能因为某一签到通过，就提前宣布依赖战斗或多人状态的整个活动族已完成。每次只对有证据、有实现和有验收的范围打完成标记。

不承诺按固定天数“写完全部玩法”。排期由可取证性、依赖和验收复杂度决定；为赶日期而补自定数值会直接改变目标。开发里程碑与玩家开服第N天是两个轴，不能把“M3完成”写成开服第三天。

## 5. 必须贯通的跨系统链路

| 业务起点 | 一次合法业务应驱动的后继 | 必须验证的失败/重试 |
| --- | --- | --- |
| 主线胜利 | 对局结果→体力/原首通奖→最后通关节点→团长经验/等级→任务/活动统计→功能/引导资格→同步与保存 | 败北不当通关；重复结算不二扣二发；结算前后断线可恢复 |
| 英雄升级/突破/升星 | 原成本→英雄/格子→技能门槛和属性→编队/战力→图鉴/任务/成长活动→面板和重登 | 材料差一份、上限、并发、编码/数据库失败全笔无变化 |
| 招募或活动抽取 | 池/期/资格→原成本→逐抽保底→对象或pending→次数/累计→记录/展示→领取/重登 | 心愿保存不算抽取；抽取成功回包丢失不能再抽；pending只发一次 |
| 游戏商品购买 | 原商品资格/限购→余额/券扣款→订单→原奖励/特权→原购买统计和资格→1900/16003及登录同步 | 同request_id重试返原订单；加钱包余额不计游戏购买；同SKU不同活动不串限购 |
| 活动换阶段/换期 | 统一时间→实例/期号→个人资格和操作门禁→在线/登录投影→原结算/继承/货币政策→审计 | 停机跨过多个阶段、重复tick、结算中断、新旧期同时请求、子活动窗口 |
| 公会/竞技共同事件 | 真实参与者/职权→共享实例/快照→战斗或合法行为→积分/排名→冻结→唯一奖励 | 同一目标并发占领/领取、离会/断线/取消、跨服请求、重复调度 |

事件名、数据库表和推送类型以当前实现及原协议为准；规划中的业务箭头是必须验证的关系，不代表每个关系已经接上，也不要求为写文档另造一套事件系统。

## 6. 每个工作包的可执行交付要求

领取子项时明确：规则ID、命令/模块/slot/表行、允许改的文件、依赖与共享接口、对应存档和客户端场景。一个模块可能同时包含已实现、兼容和拒绝分支，应按分支交付，不用一个模糊状态覆盖全部。

1. 从[表目录](rules/tables/README.md)定位原配置，核数组长度、索引、ID空间、分片与消费者；静态表没有规则时继续追脚本或已有运行证据。
2. 写出正常、门槛前后、重复、失败、跨日/期、断线/重启的独立预期。随机规则以固定随机点覆盖候选和保底，不以“抽起来差不多”验收。
3. 在隔离临时库实现/验证资格、成本、对象、统计、领取位和编码同事务；同时核资源处理器、共享作用域、回包、推送和登录slot。
4. 需要旧档调整时先输出逐角色差异、幂等键和副本演练；不得重套创角模板、批量清Guide或清全部功能位。
5. 对实际客户端走对应场景，保存包/版本、请求、UI、日志及存档结果。完成单场景和完成连续流程分别标记。
6. 更新玩法章、规则卡、命令/功能映射与实施记录，重建清单并核链接/哈希；发布时再记录上线版本与实际结果。

提交内容应包含生成器和说明，原APK、签名材料、账号/令牌与敏感存档留本地。证据包过大时文档记录精确路径、哈希和复现方式；不能以“文件没提交”作为隐去证据来源的理由。

## 7. 测试、客户端与发布门槛

| 验证层 | 最少检查项 | 不能替代 |
| --- | --- | --- |
| 文档/静态 | 链接、逐表/逐行覆盖、来源哈希、跨表引用、原值与派生值区分 | 原规则运行语义、业务测试 |
| 组件 | 独立预期、合法/非法参数、门槛边界、成本奖励、防重、错误回滚 | TCP兼容与客户端表现 |
| 临时TCP | 真实帧/编码/schema、角色上下文、回包与定向推送、登录重取 | APK能否正常消费 |
| 存档 | 重开SQLite、A/B账号隔离、快照投影、并发/重启/迁移、订单账本 | 原版数值与客户端UI |
| APK | 原入口、正常操作、失败提示、按钮/红点/已售罄、返回、连续流程及重登 | 其他版本和未走过分支 |
| 发布后 | 实际release/PID/数据/日历/包版本与目标场景 | 本地通过或五端口存活 |

测试命令从项目根目录执行：

```powershell
npm test --prefix personal-server
npm run test:all --prefix personal-server
npm run test:deployment --prefix personal-server
npm run check:command-dispatch --prefix personal-server
node tools/build-gameplay-doc-evidence.mjs
node tools/build-detailed-rule-docs.mjs
```

`npm test`是fast，`test:all`才是全部已纳入的测试文件；测试失败需区分本轮回归、历史问题和环境限制并留对照，不能改预期来迁就错误规则。文档修改本身以文档和事实清单校验为主，不因此声称重新通过业务全量。日历审计和运营命令见[运营手册](08-operations-runbook.md)。

发布的最小退出记录是“哪些原版规则已核、哪些场景已验、哪些分支仍缺、当前用户会遇到什么限制”。未验的败北UI、未定位的1级弹窗、未闭合的NPC技能等仍留在[问题表](09-defects-and-acceptance.md)；文档补全不会自动改变这些状态。

## 8. 开服首日、首周与30/90天规划的使用方式

玩家排期以[活动日历](rules/activity-calendar.md)为逐行事实入口。读者应能分别查看开服day1、day2、day3，前30天和前90天的活动窗口/阶段及未知行。当前三服开服输入是 `2026-11-12T18:00:00+08:00`；该输入只决定本服计算，不能把原表 `world_time` 的历史绝对日期改写为原版相对开服规则。

每个日次运营包包含：当日新增/结束/转领奖/转展示的实例，父子活动，原版本/期号，个人功能门槛，允许的读/操作/领奖动作，结算任务，商品与限购，货币政策，客户端倒计时和异常检查。可计算窗口中带rebase标记的部分单独列为当前本服政策；未知时间类型和业务未实现项也保留在排期审查范围内，不以强开补齐“看起来完整”的首周。

30天视图用于检查新服成长、首周到常规轮换及商品/任务的衔接；90天视图用于检查循环重叠、赛季、跨月/周、后期功能门槛和跨期继承。二者只提供基于当前资产及算法的规划视图，不能保证原服90天实际推送过的全部动态活动都已经取得。具体执行清单见[运营手册](08-operations-runbook.md)。

## 9. 当前状态与历史计划的关系

2026-11-06的[完整任务计划](../plans/remaining-gameplay-20261106/README.md)提供命令归属、子卡和历史实施记录；2026-11-12的[全功能设计](../plans/full-service-design-20261112.md)与[升级/开放/运营设计](../plans/ops-level-open-rules-20261112.md)提供共享层和运营问题拆分。这些是有日期的输入资料，不能原样继承其中未路由数量、代码行数、空载荷成功数、待取证状态或【定】策略。

当前命令归属查[全部命令](appendices/commands.md)，功能条件查[开放全表](appendices/feature-unlocks.md)，配置事实查[规则目录](rules/README.md)，业务/客户端状态查最新实施记录。静态命令数、协议分组数、已解析表行数分别是不同分母，均不能换算成玩法还原比例。

本规划的完成维护方式是：规则事实或实现发生变化时，更新对应工作包和规则卡；需要发布时附实际验收；发现旧事实冲突时保留差异与来源。只有原版可达规则、业务分支、数据同步、客户端和运营周期都通过相应验收，才能对该范围写“1:1还原完成”。
