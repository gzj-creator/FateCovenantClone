# 05 资源、任务、招募与商城

## 1. 共同原则与唯一例外

**除代金券系统外，经济与商业规则全部按原版还原。** 代金券保留本项目的邮件发放、1张=¥1、领取与抵扣机制。钱包用于个人服务器付款接入；商品价格、礼包内容、限购、首充/累充和活动领取条件按原版。管理后台加钱包余额只是加可支付余额，不是购买游戏商品。

当前所有交易应遵守：合法资格与活动阶段 → 原价格/原成本 → 原奖池或奖励 → 权威对象/资源变化 → 对应计数/限购/领取位 → 回包和在线同步 → 重登。任何一段不明都作为缺口处理，不能改价或发替代奖凑通。

## 2. 资源权威与对象型奖励

`ResTable` 决定奖励对应的资源类型与处理器。普通货币、堆叠道具、英雄、装备、圣器、外观、特权等不能都写成同一个资源余额。英雄奖需要创建英雄；装备奖需要可穿戴对象；皮肤奖需要可选外观；邮件/活动回包还要让客户端看到同一对象。

| 场景 | 应有变化 | 不合格情况 |
| --- | --- | --- |
| 领取货币/道具 | diff_num、new_num、必要new_bin与实际余额一致 | 前端显示获得但资源表没变 |
| 获得英雄 | hero对象、名册/图鉴、资源变化与编队候选 | 只有tid计数，没有hero_list |
| 重复英雄/碎片合成 | 按原规则增加、转换或合成 | 自行决定每个英雄换固定碎片 |
| 自选/选择箱 | 在原候选与版本范围内选，数量与品质合法 | 接受任意tid或把所有选项都送 |
| 随机箱/抽奖箱 | 取正确奖池、权重、保底/上限 | 所有箱子均从所有英雄随机 |
| 道具使用/兑换 | 原消耗、产出、使用资格、目标 | 背包有物品就视作任何场景可用 |
| 资源补全/回退 | 原窗口、差额、兑换和返还规则 | 代码5改空成功，没发资源 |

货币数量应避免JS浮点精度丢失，按proto和存储使用整数/BigInt字符串。金额单位统一分，不能与钻石、代金券张数或礼包展示元混用。

## 3. 任务来源与领取

任务条件由任务表与函数映射决定。客户端发来的计数、英雄战力或领奖标记不能代替服务器已发生行为；通关、养成、消费、抽数、付费、登录等必须由各权威服务发事件或查询当前真实状态。

| 任务族 | 进度范围 | 关键边界 |
| --- | --- | --- |
| 主线/线性任务 | 按前驱与下一条推进，可能含领取后解锁 | 正在挑战不算已通关；当前最后通关节点算完成 |
| 每日/每周 | 对应业务日/周的事件与领取位 | 跨05:00、周一重置、重登不清错期 |
| 成就/排名成就 | 永久累计或峰值，部分基于榜单快照 | 不能以客户端点击增加成就 |
| 首周/成长之路 | 创角或开服天数、分日目标、阶段奖 | “第几天”不能混用自然日、业务日、注册24小时 |
| 战力/等级奖 | 实际等级、合法属性与阈值 | 兼容战力不等于原版阈值计算通过 |
| 周期/活动任务 | actId、version、period、taskId | 上期进度与领奖不能直接继承，累计任务有独立语义 |
| 开服冲榜 | 真实任务统计、积分、榜单与阶段 | 活动任务奖励与最终排名奖励分开 |
| 任务组/功能手册 | 组、章节、依赖、阶段奖励 | 组领奖不能把所有子任务标完成 |
| 挂机/追回 | 起止时间、已收取点、产量、离线时限、免费/付费档 | 领取后原子移动时间游标，失败不得丢累计 |

领取先校验达标再写领取账本和发奖，同一事务内保存。仅更新领取位但未解析奖励属于数据损坏；旧记录需审计并按实际缺失补偿，不能再领一次叠加正常奖励。

## 4. 招募与奖池

普通、精英、友情、新英雄限定、圣器、神灵/天极、幻武及活动抽取分别有奖池、成本、解锁、保底和记录，不得共享一套全英雄池。

当前 `recruit-pool-rules` 对 lib1/2/3/10 有本地兼容品质矩阵、解锁/心愿逻辑；普通池已排除 newHeroExclusive 组。这个排除本身不能证明池内名单与概率已经1:1。DrawTable的部分Group/范围仍未恢复，不能把代码矩阵作为原版概率公布。

每个奖池必须整理：

| 项目 | 需要的确切规则 |
| --- | --- |
| 版本与开放 | lib/version、活动期、功能条件、开服日、普通/限时切换 |
| 候选 | 品质/阵营/获得方式/排除组、具体英雄、可达形态 |
| 成本 | 免费次数、券种、钻石代购、单抽/多抽、折扣、每日上限 |
| 概率 | 分层权重、组内权重、稀有解锁、权重是否随计数变化 |
| 保底 | 计数起点、命中重置、跨池/跨期继承、定向与普通独立 |
| 心愿/自选 | 开放门槛、槽数/品质、候选、替换、是否必定命中心愿 |
| 重复处理 | 本体/碎片/兑换币，首次与重复的差异 |
| 累计奖励 | 总抽数/本池/活动期计数、里程碑、领取位 |
| 展示/记录 | 展示顺序、弹窗、获得对象、抽取日志、重登和重试 |

静态写有心愿选择不能当作“选谁必出谁”。多抽须明确保底在每一抽后更新、是否保底品质叠加、是否有首抽固定奖励；不能先抽十个再统一判断一次。

圣器/神灵等共享draw resolver已有部分生产路径；空的lib_range、神灵226等未闭合处仍需取证。随机过程可用固定种子验证边界，但不能仅用概率大样本证明候选和保底流程正确。

## 5. 普通、活动与神秘商店

商品关系至少包含 shopId、goodsId、item/reward、price/currency、购买次数作用域、刷新、资格和活动期。展示列表与购买校验必须使用同一配置与周期键。

普通商店需还原固定/随机商品、手动刷新、自动刷新、刷新价格阶梯、免费次数、历史商品、快速购买和批量购买。神秘商店与个人刷新种子独立，不得每次打开任意换货。活动商店按活动货币与结束领取窗控制，不能仅看页面可见就允许购买。

限购分别处理终身、自然日/业务日、周、期、活动、额外补货。终身限购不随活动换期归零；一键礼包必须在同一事务校验并消耗各子礼包额度，免费子礼包是否包含以原配置为准。

自选内容应先保存还是随购买传入、变更后是否影响已购待领、未选时是否可买，均按原脚本。禁止以“缺少自选参数”为由发默认最强奖励。

## 6. 充值与福利类型

| 类型 | 原版必须保留 |
| --- | --- |
| 钻石/龙晶充值 | 价格、首购/双倍、付费货币分类、购买记录、累充口径 |
| 首充/连充/累充/单笔 | 达标依据、天数/次数、免费/付费领取位、可补领规则 |
| 每日特惠/限时礼包/升星礼包 | 触发条件、版本、有效期、子礼包限购和补货 |
| 月卡/永久卡/免费特权 | 激活期、日奖、错过能否补、到期/重复购买叠加 |
| 通行证/新通行证/月通行证 | 期号、任务经验、免费/付费轨、买级、自选、结算与邮件 |
| 基金/理财/钻石银行 | 购买资格、返利/最低保证、日程、已取历史 |
| 团购/热度/砍价 | 真实订单人数/金额、全服与个人资格、阶段发奖 |
| 返利/重置 | 消费金额来源、可重置记录、折扣、不可重复回溯 |
| 皮肤/外观/助手 | 指定对象、拥有/穿戴、试用与期限、重复转化 |
| 拍卖/订阅 | 跨玩家场次、出价、配额、赢家、结算、退款/分红 |

这些类型不是“购买后统一发一包资源”。付费会激活资格、每日/后续领奖与登录模块。商品本身、额外首充、每日特惠、活动任务和累充账本可能同时变化，必须分别按原触发条件处理，不能靠遍历所有活动给奖励。

## 7. 定制代金券与钱包的精确边界

| 项目 | 本项目定制规则/现有路径 |
| --- | --- |
| 面值 | 道具701500，1张=100分=¥1 |
| 发放 | 管理端发行，通过真实游戏邮件领取入背包 |
| 抵扣 | 原生16004入口与管理购买路径；数量须为整数，不能超价格或持有数 |
| 钱包 | 后台加余额，再按实际商品购买扣款；不等于外部真实银行卡支付 |
| 混合支付 | 管理购买可用券+余额，二者合计等于商品价 |
| 对账 | 发券/邮件、领取、可用券、核销、余额扣款、商品订单分别记录 |

玩家实际购买时才产生游戏购买与其对应的资格/累充记录；后台给钱包加款不能算累充。当前原生成功链有16004→1900→16003的历史客户端证据，不能用它证明每种商品都已打通。

用券后某商品是否进入特定原活动统计，需要遵循既有代金券定制口径并保持原商品判断与门槛；不得把兑换币、钱包余额、优惠后余额支付额和商品标价混成同一个字段。当前代码的统计行为要逐类型对账，有差异先登记，不能擅改成“所有0元都算充值”或“所有用券都不算”。

## 8. 订单幂等、到账与异常

购买以账户+request_id唯一；重复同一请求返回原结果，参数不符应拒绝。限购、扣款、核券、发奖、商品/特权与活动记录应在同一事务。编码或数据库失败全回滚；线上推送失败不能导致再次发奖，应从已提交状态补同步。

断线后查订单与实际对象，再确定“未购买 / 已购买待同步 / 已到账”。不能让玩家换一个request_id重买来解决未到账，也不能在不知道旧交易状态时全额补两次。

当前管理端没有通用退款或任意英雄补发HTTP接口，运营不得编造路径。补偿必须先出对象、来源、差额与幂等预览，按[运营手册](08-operations-runbook.md)处理。
