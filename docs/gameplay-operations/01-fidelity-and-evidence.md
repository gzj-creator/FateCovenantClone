# 01 还原范围与证据标准

## 1. 交付目标

用户要求按原游戏规则玩到相同的流程节点，遇到相同的关卡、敌人、奖励、养成约束、功能开放和活动阶段。服务器应兼容已有原客户端的界面、演出和数据读取方式。不能将“接口有返回”“大厅能打开”“测试全绿”解释为完整还原。

2026-11-14 用户补充：**除了代金券系统，都要 1:1 还原。** 这覆盖此前采用本地兼容玩法的临时做法。代金券发放、邮件领取、面值与抵扣保留定制；钱包提供个人服务器的付款渠道。其他商品与充值规则按原版还原，包括商品价格、礼包内容、限购次数、首充和累充的领取条件。后台加钱包余额不是一次游戏商品购买，不应凭空发放商品或增加游戏内累充。

2026-11-15 用户进一步要求统一真实点并为所有未明确项定下唯一执行基调。有效裁定以[最终规则基线R1](12-final-rule-baseline.md)及[逐任务裁定](rules/final-rule-register.md)为准：原证据能证明的按原规则；原服务器未提供的部分执行明确标识的复刻推定或具体分支限制。证据限定继续如实保留，不能以已作选择冒称原版算法已恢复。

| 维度 | 必须对齐的细节 | 验收对象 |
| --- | --- | --- |
| 创角 | 初始英雄、资源、等级、经验、阵位、默认外观、系统进度 | 全新账户首次登录与第二次登录 |
| 新手 | 触发条件、引导顺序、奖励请求时点、上阵提示、失败恢复 | 从首次创角连续玩过第二章关键节点 |
| 关卡 | 战斗与剧情区分、NPC、阵位、属性模板、技能、固定友方、特殊规则 | 地图、布阵、实际战斗、胜负界面 |
| 战斗 | 行动顺序、目标、伤害/防御通道、怒气、技能解锁、被动与状态、胜负 | 输入快照、服务端轨迹、原版对照、客户端回放 |
| 养成 | 物品归属、消耗、等级上限、突破与升星、属性与技能变化、返还 | 操作前后资源、对象、面板、战斗、重登 |
| 经济 | 任务触发、首通、扫荡、抽取、保底、重复转化、自选、限购 | 同一笔扣费、发奖、进度、账本与推送 |
| 社交竞技 | 真实玩家、公会、对手、匹配、排名、周期与奖励 | 多账号隔离、并发、跨日、重启、结算 |
| 活动运营 | 预热/进行/领取/展示、排期、个人资格、付费路径、过期转换 | 开服日、各边界时间、在线变化、离线补结算 |
| 表现 | 名称、模型、人数、战力、怒气比例、提示、失败与返回入口 | 真实 APK 截图、录像、日志 |

“1:1”以明确的版本为范围。原客户端 `1.55.090365`、历史提取包和隔离 APK 修改版本可能不是同一份字节。每份规则均需记录来源版本、文件哈希和适用范围；不能把跨版本配置拼成所谓原版标准。

## 2. 证据种类

| 标记 | 意义 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 原版配置 | 原客户端静态表、字符串、proto、命令注册表 | 版本内字段、ID、配置数值、注册关系 | 原服动态策略、入口一定可达 |
| 原版脚本 | Lua/IL2CPP 读取与处理逻辑 | 条件、调用顺序、计算方法、数据消费者 | 未执行的分支在当前服一定发生 |
| 原版观察 | 已保存的正常游戏录像、截图、被动通信 | 具体账号、时间、操作下的真实行为 | 未观察的等级、活动期或账号行为 |
| 当前实现 | 个人服务器源码与配置 | 我们目前如何处理 | 处理是否与原版一致 |
| 复刻裁定R1 | 统一基线、逐任务决定与版本化实例 | 本项目遇到缺证据分支时必须怎样执行 | 原服隐藏算法已取得或本轮已改业务 |
| 组件验证 | 单元、服务、编解码、事务测试 | 特定输入的行为与错误回滚 | 客户端接受和原版一致 |
| 链路验证 | 临时 TCP + SQLite + 重开 | 协议与持久化闭环 | 当前线上部署、视觉与长期玩法 |
| APK 验收 | 隔离客户端实际操作、截图/录像、日志、存档 | 具体版本和场景下可玩 | 未走过的所有场景 |

没有原服后端源码时，客户端声明也可能只是展示或预测。例如 `MissionTable.Section.enemy` 是地图展示所需字段，不能当敌阵；`GuideAwardStep` 领奖成功后才结束步骤，不能倒置为“先结束才允许领奖”。这些必须通过消费者脚本核对。

## 3. 规则冲突的处理

先核对版本是否一致，再比较原配置、读取脚本、实测三者。静态表与观察不符时建立差异记录，说明观察账号、开服天数、活动/难度与是否存在服务端覆盖；不得静默挑选更容易实现的一方。

旧设计、当前实现和原版事实不争夺同一身份：当前实现只说明代码现状；R1说明目标动作；同版原消费者说明原语义。与R1冲突的旧运营建议已撤回，历史实现记录保留日期且不再作为发布输入。新的原证据改变某项推定时必须升级规则版本并列差异，不能悄悄改变已有实例、抽取或订单。

每条事实应能追溯为：来源路径与 SHA256 → 表/函数 → 关键输入 → 预期行为 → 当前结果 → 验证产物。原始敏感流量留在本地，文档只摘取必要字段，不提交令牌、手机号、管理密钥或用户完整存档。

## 4. 完成口径

采用分项记录而非一个“已完成”标签：

| 项目 | 允许填写的状态 |
| --- | --- |
| 规则取证 | 未取证 / 配置已取 / 脚本已核 / 运行已核 / 存在冲突 |
| 业务实现 | 未实现 / 明确拒绝 / 兼容实现 / 部分按原版 / 全分支已实现 |
| 数据同步 | 未核 / 回包已核 / 在线推送已核 / 重登已核 |
| 原子性 | 未核 / 资源与状态一致 / 编码异常回滚 / 数据库异常回滚 |
| 客户端 | 未验 / 单场景通过 / 连续流程通过 / 回归通过 |
| 发布 | 未发布 / 已发布待验 / 已验收 / 已回滚 |

某个命令“明确拒绝”可以证明没有伪造成功，但仍是玩法缺口。带证据缺口的“服务端完成”保留原记录，并拆解缺失项，不继续作为整卡销项。

## 5. 已知本地规则必须显式标记

当前源码存在以下需要替换或核证的行为，详见相应章节：

- 旧主线敌人使用地图展示字段、玩家平均属性乘 `0.88` 和玩家最高等级；当前工作树普通主线守方已替换为原Fight/Team/NpcAttr链，其他模式的兼容路径仍逐项核对。
- 旧三个关卡借用前关敌人：30204、40203、40210。当前工作树已恢复对应原版 Team 并移除普通主线借关；旧“原包没有这些行”的结论不再沿用。
- 英雄基础属性缺目标品质时选邻近品质，职业速度由本地函数估算。
- 战斗内部分职业技能、暴击率、复活比例等仍有本地 profile；通用被动的突破解锁映射未闭合。
- 普通招募的部分奖池为显式兼容矩阵，不能将矩阵权重公告为原游戏真实概率。
- 一些公会、活动玩法有本地伤害、次数、奖励、周期策略；“待证”仅说明原证据未取得，具体允许与拒绝动作已经由R1逐任务固定。

把这些数字写进文档是为了便于发现和替换，不能让它们取得原版规则的地位。

R1明确保留的职业速度、怒气和防御伤害兼容通道按锁定源码执行，不能随意另选数值；未获明确许可的本地经济、随机和养成常数不能借“兼容”继续扣费。完整数值与范围见[最终基线](12-final-rule-baseline.md#battle)。

## 6. 还原实施顺序

第一优先是新号从创角到第二章的连续链路。其次统一关卡/NPC/属性/技能数据，再接通任务、奖励、商城与各玩法。活动排期、商业系统、后期数值必须建立在可靠的资源、功能开放和战斗基础上。

不能先把所有入口打开再声称覆盖。也不能因某张表解析为空就断言原版没有配置：本轮 Fight/Team 第 0 分片便是字段映射错误导致空对象，修正解析后可读出各 988 行。

## 7. 文档与证据的可重建性

文档附录生成入口：[build-gameplay-doc-evidence.mjs](../../tools/build-gameplay-doc-evidence.mjs)。在根目录执行：

```powershell
node tools/build-gameplay-doc-evidence.mjs
```

输入包含本地分析文件；缺原始文件时不能凭空生成替代数据。生成器校验派发审计的源文件哈希，输出引导、早期关卡、功能开放和全部命令附录。对表值进行检查还需行数、字段类型、数组对齐、跨表 ID 和消费者语义核对；仅 JSON 格式正确不够。
