# 04 英雄、编队与完整养成

## 1. 英雄身份、格子与归属

`hero.tid` 是角色配置，`hero.uid` 是玩家拥有的具体对象；同名战斗 NPC 的 tid 又是另一空间。品质、星级、稀有形态、等级、突破、专精等分别保存，不能把品质当星级、把目录中存在的角色当已经获得。

原客户端部分等级/突破养成作用于编队格子，服务当前 `cellHeroes` 根据格子索引找到预设阵容中的英雄同步；星级作用于英雄对象。实际各阵容/模式的继承规则应按客户端核对，不能把“换人后格子等级继承”误写为每名英雄独立重复消费。

| 对象 | 必须保存 | 必须检查 |
| --- | --- | --- |
| 英雄 | uid/tid、数量、等级、品质、星级及进度、突破、专精、形态、装备关联 | 拥有关系、解锁、上限、同对象不能重复消费 |
| 养成格 | index、level、break_level | 可用格、指定英雄确实在格中、跨预设同步范围 |
| 编队 | play_type、预设索引、team_index、loc、fighter、出战附属物 | 当前模式上阵人数/阵位、互斥、租借、保存与当前选中 |
| 道具/装备 | 具体 uid 或资源 tid、数量、品质、等级、穿戴对象 | 不可把同一件物品同时给多人，分解穿戴物按原限制 |

## 2. 编队操作

当前已实现普通预设和自定义编队的部分路径。208/209/218 是早期已验证入口；完整 LineupCmd 见[命令附录](appendices/commands.md)。登录 module9 外层是 `pb_lineup_login`，内部 `pre_lineup` 再编码为角色编队对象，不能把嵌套 bytes 当扁平阵容。

流程为选择玩法/预设 → 选择英雄与位置 → 按原规则校验 → 保存 → 更新属性与战力 → 战斗入口读取同一份阵容。已获得未上阵、已上阵但未保存、历史快照与当前预设是不同状态。推荐阵容/一键上阵只能按原选人和排序规则，不得为方便通关偷偷加入赠角或替换英雄。

需对照的细节包括前后排位置、总人数、队数、后备位、相同英雄/同系英雄限制、援助和租借有效期、圣器出场顺序、宠物/精灵出战位，以及固定剧情阵容的覆盖范围。不能把引擎支持“最多12名单位”直接当每个模式允许的上阵人数。

## 3. 等级、突破与升星

当前规则来自 HeroTable 的 UpLevel、UpStage、UpStarCost、UpStarStone、DevelopConst、Star。数值表与消费者要同时核对；下表是现有实现和需验证处，不把所有代码上限自动视为原服事实。

| 操作 | 当前实现要点 | 还原验收 |
| --- | --- | --- |
| 升级636 | 指定格子；逐级累加 UpLevel.cost_item；受团长等级×hero_lv_rate、下一突破门槛约束 | 单级/批量同消耗，越界全笔失败，所有应继承英雄同步，属性与技能等级正确 |
| 突破638 | 检查 UpStage 对应等级和成本，增加 break_level | 当前/下一阶索引与首阶边界准确，潜能/技能解锁同步 |
| 普通升星639 | 使用英雄碎片；当前每星6段，按品质与星级成本，最多补足剩余段 | 一次多段与分次总消耗一致，满6段进星，不越过试炼阶段 |
| 5星后路径 | 普通639拒绝跳过，另走觉醒/试炼相关命令 | 原门槛、试炼进度、升星石种类与数量、最高星、形态变化全链核对 |
| 觉醒选择 | 客户端可只选材料种类，数量来自配置，不能相信请求自填数量 | 非法石、不足、重复选择、差一份材料均正确失败 |
| 批量/一键 | 逐项遵守相同规则和成本 | 已证原部分成功语义则从原规则；未证时按R1整批原子提交，失败全部回滚 |

当前实现有等级300等边界，但不应将所有英雄、版本和玩法都强制同一上限。每个英雄 max_star、品质、变异、特殊养成以原表为准。

升级/升星必须同步英雄、格子、资源、红点、任务统计、图鉴/羁绊、技能、面板、战力和保存。只改英雄等级显示而战斗属性不变属于未完成。

## 4. 专精、魂/稀有形态与技能

专精依赖 Mastery、MasteryGroup、MasteryLevel、MasteryBreak、MasteryConst、MasteryMat；要区分解锁星级、等级、突破和选中技能。魂/稀有形态可能替换主动技能而非额外叠加两套。当前 `hero-skill-loadout` 已接 AbilityLevel、部分 mastery/soul，但普通被动的突破对应仍未闭合，详见[战斗章](03-combat-and-attributes.md)。

重铸需恢复属性池、抽样权重、锁定词条成本、暂存与确认、替换/取消、免费次数和上限。预览不能扣正式养成；确认才提交。原版没有的“刷到满意自动保存”不可自行加上。

## 5. 图鉴、羁绊、好感与支援

| 系统 | 完整循环 | 关键待核细节 |
| --- | --- | --- |
| 英雄图鉴/团员名册 | 获得或满足条件 → 激活 → 提升 → 领奖 → 属性生效 | 持有/曾持有判定、星级记录、章节分页、全队作用域 |
| 推荐阵容/流派 | 查看条件 → 激活/选择 → 满足里程碑 → 领奖 | 选中状态与领奖分开，周期/版本、当前编队与历史获得区别 |
| 羁绊 | 指定英雄/形态达到条件 → 激活 → 属性/技能 | 是否需要同时上阵、等级、替代角色与重复计算 |
| 好感/训练 | 赠礼 → 好感值 → 等级/突破 → 奖励/属性 | 礼物喜好、上限、溢出、批量、派对/游乐场资格 |
| 亲密/约会剧情 | 解锁对象 → 消耗次数/道具 → 事件/剧情 → 领取 | 成功/失败、支线选择、是否可重播、跨日重置 |
| 访问/碎片 | 达标英雄 → 消耗访问次数 → 获得对应碎片 | VisitUnlock、Visit奖励、每日次数和刷新时点 |
| 支援/租借 | 设置 → 借用 → 使用 → 归还/到期 | 来源玩家、租借期、次数、模式限制、本人是否仍可使用 |
| 阵容/英雄快照 | 保存时冻结 → 展示/分享/使用 | 升级后旧快照是否变化、租借状态有效性、模式版本 |
| 战术/光环/纹章/传奇书 | 激活 → 等级/天赋/星级 → 出战/全局属性 | 消耗、解锁、技能、重置返还、属性归属与版本 |

这些系统的协议卡和当前服务路径已完整列在[全模块目录](appendices/modules.md)；仅有领取位而没有真实奖励、仅写等级而未入属性不能视为完成。

## 7. 养成资源与返还

任何消费先校验全部成本与目标，随后一次事务提交。不能先扣材料再发现装备槽位不支持。与资源处理器没有映射的奖励必须作为阻断项登记，不能仅写领取位或返回空资源成功。

重置/回退/分解应有预览与执行一致性、精确返还规则和幂等键。某系统原版不全额返还时不能自行改全返；原版应全返时也不能为了经济平衡扣手续费。包含随机词条、租借、穿戴和锁定对象的返还需要逐项原版证据。

## 8. 每套养成的验收模板

准备低阶、门槛前一档、正好达标、满阶四种合法存档；分别验证单次、批量、材料不足、重复请求、断线、重登和替换编队。核对成本、目标对象、关联对象、技能、属性、面板、战报、任务统计与实际SQLite。每个未知字段标待取证，不给默认有利值让用例通过。
