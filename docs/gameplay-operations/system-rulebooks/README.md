## 规则的证据标记

文中“原表”指已经读取的配置字段；“原客户端函数”指从本地脚本恢复的消费者。两者可以确证配置与客户端的运算方式，不能单独证明原服隐藏逻辑。“当前实现”用于记录服务端实际取数与提交方式；其中注明兼容值、本地策略或未接入的部分，不属于原版规则。写到“必须补证”时会给出缺失表、字段、函数或运行场景，避免把一个未知泛称为已完成。

例如，`NpcAttr20.attr_list`确证蜜雪儿的基础模板；她的`Npc_Ability`另有属性技能，所以“基础HP864”不能直接当作原服最终战斗HP。`ShopItem.price`确证价格数组；如果数组的阶梯解释只有本地消费者而未与客户端核对，必须保留这层边界。

## 每项规则共同遵守的执行顺序

1. 确定角色、区服、模式、期号及目标实体，读取权威状态与本次使用的原配置行。
2. 检查功能/阶段/前驱、拥有权、数量、成本、上限、目标和重复记录；客户端展示与传参不能代替检查。
3. 在一个事务内扣成本、变更状态、发奖励、记统计与唯一领取/订单标记，并完成回包编码。
4. 提交成功后发送通知。通知失败保留已提交结果，通过重试、补同步或登录投影恢复。
5. 重新登录按持久化记录重建状态；重复请求返回既有结果或明确已完成，不再扣款或发奖。

事务要求是本项目的实现约束，不等于已经获知原服数据库结构。跨玩家对象还要在共享实体上竞争同一个扣减/领取条件，不能仅在每位玩家自己的存档中各记一次。

## 读数时的六个边界

| 边界 | 具体要求 |
| --- | --- |
| ID空间 | 角色ID、英雄uid、英雄tid、NPC tid、Fighter tid、Item tid、表行tid、功能ID分别校验；名字相同不能混用 |
| 时间 | 业务日、自然日、开服日、创角日、赛季期号各自取对应消费者；不能全按UTC零点重置 |
| 百分比 | 根据`AttrType.value_type/show_factor`解释，常见10000为100%；NPC固定`{type,value}`倍率是直接乘数 |
| 奖励格式 | `[[tid,count]]`与`award/award_n`平行数组分别解析；空表、缺字段、0值不是同一含义 |
| 状态投影 | SQLite业务行、登录模块、在线push与客户端位图必须指向同一结果；模块相邻slot不是同一种数据 |
| 完成口径 | 原表已提取、组件通过、临时TCP通过、APK实际验收、发布后验收分别记录；不能互相替代 |

## 文档仍能精确表达的未知

完整原服服务端未随APK提供。原算法缺证据的状态继续保留，R1已经决定每个具体分支按原表执行、采用列明兼容或拒绝无依据的新变更；不能把“未知”留给实现者另造数值。兼容速度/怒气/防御通道与升级突破索引按主基线锁定，随机/价格/奖励不以常见游戏规则补空。[问题验收清单](../09-defects-and-acceptance.md)继续记录实现与客户端状态，本轮不部署或迁移运行库。
