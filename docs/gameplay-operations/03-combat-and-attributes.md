# 03 战斗、属性、技能与战报

## 1. 一场战斗的数据来源

普通主线的正确入口是 `mission_fight_req.mission_id → MissionTable.Section.fight → FightTable.Fight → Team → Npc/NpcAttr/NpcAttrRatio → 属性计算 → 技能装配 → 战斗轨迹 → 战报 → 结算`。展示字段、实际战斗数据和结算奖励有不同来源，不能相互替代。

| 数据 | 需要恢复的原版细节 | 当前风险 |
| --- | --- | --- |
| Fight | 类型、场景、阵型、出战限制、固定攻方、敌方多队、等级覆盖、结果/跳过/退出规则 | 已接普通主线守方链；固定攻方、场景与特殊覆盖语义未完全恢复，多队暂明确拒绝 |
| Team | NPC ID、位置、NpcAttr 键、队伍顺序 | 已替换Section.enemy和借邻关路径；原顺序保留 |
| NPC | relation_hero、精英标记、技能、外观引用、属性倍率 | 已关联原NPC与外观、保留role_type=2；NPC技能执行和属性能力未闭合 |
| 英雄 | uid、tid、品质、等级、突破、星级、专精、稀有形态和装备归属 | 模板默认值或未解锁技能可能被误用 |
| 对局 | 类型、双方真实阵容、随机种子、特殊规则、模式期号 | 多玩法不能共用一个胜率或战力比公式 |
| 战报 | 初始值、每次动作、HP/盾/怒气、死亡、结果、各队战力 | 界面与模拟可能读取不同战力链 |
| 结算 | 实际胜负、体力/次数、首通、阶段、资源、任务和排名 | 报告生成与持久化重复或遗漏 |

当前[mission-fight-service](../../personal-server/game/mission-fight-service.mjs)已调用[fight-team-resolver](../../personal-server/game/fight-team-resolver.mjs)恢复普通主线守方的`Fight→Team→NpcAttr→CalcValues`，战报FightID由Section配置决定，忽略客户端不符的fight_tid。精英等其他encounter仍有旧兼容路径，未一并宣称还原。

## 2. 敌阵与属性模板

之前把register0共享数组当字段映射，行被解释为空对象，误记为原客户端缺表；该结论无效。新解析器定位含tid的field map，打包Fight3566、Team10744、Fighter4518、AttrAbility1099行。Team91102已提取，其是否覆盖玩家攻队仍待运行证据。所有数组必须对应：NPC数量等于位置数量；多队保持原顺序，当前普通主线多队明确拒绝，不能只取第一波算完成。

NpcAttr由Team.team_lv选择；原CalcAttr的NpcAttrRatio索引为传入NPC tid×10，不是FighterID×10。NpcAttrRatio与上下文pair倍率除10000，固定调整{type,value}的value直接乘，不能全按百分比处理。relation_hero只提供外观/英雄配置，不是玩家uid；NPC技能从Npc_Ability与Fighter.add_ab取，不无条件装配同名英雄全部后期被动。精确NPC技能效果及AttrAbility增量仍待接入。

旧主线使用玩家均值×0.88与玩家最高等级造怪，本轮已从普通主线路径移除。独立回归核蜜雪儿NPC3030500/位置5/HP864、2-1原四人/HP474，玩家升级与改变队伍后敌方模板和战力不变。其他模式仍有此兼容策略，必须逐项替换；不能把主线修复扩写成所有战斗已还原。

## 3. 属性分层与定点数

原版区分显示属性、actor 属性和战斗属性编号。HP、攻击、物防、法防、暴击、暴伤等不能靠同名字符串跨域混用。当前 `ACTOR_ATTR.HP=1`，战斗 HP 为 24，是不同空间；actor 的 24 是物防。必须使用 AttrType 映射。

配置中的百分比按 value_type 和 show_factor 解析，已恢复的定点比例通常 `10000=100%`；不能将所有整数都除 10000。百分比折入平值与每阶段取整顺序必须按客户端 `AttrCalculator` 保留。例如当前恢复的 `calcAttrValues` 对 HP/攻击/物防/法防执行 `floor(flat×(1+percent))` 再移除相应百分比项；面板其他层级加成仍要审计。

| 属性来源 | 应核对的内容 |
| --- | --- |
| 本体/品质 | 精确品质基础行、成长、等级系数和上限 |
| 星级/突破 | 里程碑、阶段百分比/平值、是否作用于格子或英雄 |
| 技能属性 | 仅装配已解锁能力，正确技能等级与被动作用域 |
| 装备/团长装备 | 每件物品的实际拥有者、穿戴位、全队或单人范围 |
| 图鉴/好感/羁绊/训练 | 激活条件、永久累计、编队限制与归属 |
| 圣器/幻武/符文/法阵 | 对象等级、槽位、阵型和模式限制 |
| 宠物/精灵/秘宝等 | 全局加成与出战效果分开，不能重复叠入 |
| 模式加成 | 赛季/副本指定调整、敌我区分、租借规则 |

当前装备按 `pb_lineup_fighter.equip_ids` 逐英雄归属。曾有全队重复计数适配已被移除；不能再次把全背包装备加给每名英雄。英雄属性缺品质用邻近行、职业速度兼容函数、物防与法防取平均进入单通道引擎等均需替换或原版核证。

## 4. 战力显示与 0 战力

战力既是属性计算结果，也是多处界面的消费者输出，不能当战斗伤害公式。应逐项对齐：英雄详情、属性查询1316、编队总战力、开战双方、结算对比、排行榜/匹配所需战力。虚拟团长、召唤物、禁用单位是否计入须按模式核对。

原客户端FightResultMissionForm调用CombatPowerCalculator.GetDefTeamPower(report.tid,队伍序号)，经HeroPowerCalculator读取floor(NpcAttr[Team.team_lv].power×NPC数)并应用难度倍率。本地同版原表NpcAttr1–47的power均0，2-1选NpcAttr12，因此原静态路径会算0；Custom对应def_power为空。不能只修服务端def_power就称界面修复，也不能声称已恢复原服正数算法。

离线候选只在静态战力不大于0时读取最终队战报的正数def_power；原静态正数路径与难度倍率保持，战报路径不重复倍率，缺失/零/负战力不填正数。32/64位共18项指令解释通过，两份候选bundle各核10928个TextAsset，只有目标脚本改变。此为用户报告的显示修复候选，会改变早期原静态显示行为；没有客户端Lua运行或APK验收，未安装、未发布。详见[补丁与原始证据](../../agent/workflow/gameplay-rules-20261114/defeat-power/README.md)。

接入与验收仍需同时检查：

1. 败北战报 `fightTid` 是否是 Fight201 等正确 ID，而非 Section20201 或战报流水 ID。
2. Fight/Team/NpcAttr 读取是否完整；各队索引与第一队是否一致。
3. 静态 template power 与属性重算战力是否存在不同规则，以及 `mask_def_power` 是否控制展示。
4. 客户端修改包是否缺失或改坏对应表/计算脚本；当前 APK 与取证表是否同版。
5. 胜、负、退出、重试的结果界面是否读取同一条完整链。

在没有敌人或原版明确隐藏战力的场景，0/隐藏可能合法；用户所述“有敌方第一队但显示 0”不能通过填常数或复制我方战力解决。验收需要实际失败界面证据。

## 5. 技能选择与解锁

角色技能不能仅按图鉴技能目录全装配。原 `Ability`、`AbilityLevel`、`UpStageTalent`、mastery/soul 字段分别决定普通攻击、主动、被动、属性技能、专精与替换形态。

当前 skill-database 快照含 76 个英雄、1076 条技能引用；277 条标记 `requiresInvestigation`，75 条来源为 `project-fallback`。目录数量表示采集规模，不表示这些技能正确实现。普通被动仍以 `catalog-passive-unmapped` 装入并 `levelKnown=false`，突破门槛关联未闭合。新号与低突破英雄可能因此使用未解锁效果，属于 1:1 必修项。

本轮完整扫描174个Ability/AbilityDes/AttrAbility分片、解析失败0；Fight102敌技能1900110101/2900550111只有Ability分类、没有AbilityDes，des_redirect=0。不能用相同动画或职业模板补写目标/伤害。FirstFightCustomize仅绑定GuideAnimScene演出战90022/90023，不是Fight102必胜机制；Custom102.custom_star=5也没有已证明的主线属性增强消费者。相关未证事实不能用来给新手加属性。

每个英雄需维护技能卡：原始能力 ID、目录 ID、等级/突破/星级门槛、目标、次数、倍率、怒气消耗、前后阶段、状态 ID、叠层、驱散、死亡清除、持续时间、触发优先级、与专有领域的组合。缺失倍率或 `{0}` 不能按职业 profile 填上并标完成。

## 6. 行动与战斗效果

下表是核验项目，精确公式、优先级、上限以原脚本/配置和对照为准：

| 过程 | 必须还原的细节 |
| --- | --- |
| 初始 | 初始 HP/盾/怒气、先手、开场被动、召唤、技能冷却、模式修正 |
| 回合开始 | 持续伤害/治疗、控制时长、领域、复活、触发计数重置 |
| 行动前 | 速度/位置同值规则、控制、沉默、嘲讽、行动替换与目标过滤 |
| 命中与伤害 | 物理/魔法/真实通道、命中/闪避、暴击/抗暴、增伤减伤、无视防御、护盾与上限、整数取舍 |
| 治疗/护盾 | 治疗加成与减疗、实际治疗和过量、盾叠加/覆盖/摧毁、护盾伤害归属 |
| 受击与死亡 | 反击、吸血、反伤、怒气变化、免死、替死、复活、击杀追击 |
| 行动后 | 连击/额外行动、buff扣回合、事件去重、防递归 |
| 回合结束 | 持续效果、领域期限、胜负判定、超时与平局规则 |

当前引擎怒气使用上限 1000、初始 500、行动增加 250、受击 80；其中客户端进度比例 `skill_base=1000` 已有静态证据，不能据此自动证明全部初始值与增益规则均为原版。对每个值分别追来源。

天极值、超凡生命、领域、专属叠层、额外行动已有部分实现；初始值/上限、未定价天极技、若干领域、协狩、复制、追击次数与报告投影仍有缺口。修低阶主线不应顺带假定后期技能都已还原。

## 7. 请求、战报与结算

普通主线当前协议流程：201 `fight_start` → 客户端回放 → 207 `fight_settlement` → 202 `fight_exit`。查询/分享/历史报告有独立命令和服务；不同模式的 finish/stm 要按客户端确认，不能所有请求都走同一个普通主线分支。

201 回报 `finish=false` 时客户端才请求207。创建预览战报不得提前扣费和推进；207 在同一事务内完成真实结果、消耗、奖励、进度、必要领取记录和序列化。202 清理战斗场景，不能替代207提交。重复207应返回已结算状态或按原错误约定处理，不能二次扣体力。

| 战报字段/事件 | 一致性要求 |
| --- | --- |
| fighter | 唯一 id、原 NPC/英雄 role、team/team_index、loc、外观、品质/星级、初始 HP与技能 |
| ACTION_BEFORE/AFTER | 动作 id、施法者、目标、技能类型和实际结果对应 |
| HARM/HEAL | old_hp、新 hp、盾、实际值、正确提示类型，不靠伤害负数模拟治疗 |
| BUFF_CHANGE | 原 buff tid、施加者、层数、增/删方向、清除原因 |
| SHIELD/ATTR_SYNC | 新盾量、怒气等可回放值与模拟一致 |
| DIE/RELIVE | 死亡后不可普通行动，复活顺序和 HP正确 |
| BATTLE_OVER | 胜负、回合、final_hp、最终战报与结算相同 |

客户端虚拟 captain fighter 是圣器 HUD 读取所需结构，不能当作多送一个玩家英雄，也不应影响队伍实际人数与伤害。

## 8. 随机、回放与持久化

同一输入快照与种子应可重演；记录实际参与对局的属性与技能版本，不能在玩家升级后用新属性重算旧录像。种子固定用于回归，不代表原版随机算法已复原。抽奖随机与战斗随机不能互相消耗同一条不透明序列。

战报流水 ID、Fight配置 ID、Section ID 和结算票据应分别保存。当前普通 pending 部分状态在服务实例内存，服务重启后未结算如何恢复仍需审计；历史战报服务存在不等于所有模式待结算票据已持久化。重连、中断、报告保存失败、结算后回包失败都需独立用例。

验收必须含原阵容和原技能的独立预期，不能只重写测试使它认可当前平均敌人属性。重点用例见[验收表](09-defects-and-acceptance.md)。
