# E9-2 命令到 FunOpen 功能映射取证

结论：已从客户端 LuaJIT 字节码导出 185 条有静态证据的命令门禁规则。14 条在同一 prototype 内直接同时出现 `FunOpenMgr:IsOpen` 与命令发送；171 条来自同一管理器内唯一 FunOpen id，且命令命名与该 id 的功能命名吻合。其余发送点证据不足或存在多个 FunOpen id，不生成规则，后续仍 fail closed。

## 结果

- 有规则的命令：185 / 1407。
- 同 prototype 直接证据：14 条。
- 同管理器唯一 FunOpen id 且命名吻合：171 条。
- 可解析 FunOpen 模块中识别到命令发送点：431 条。
- 发送点缺口：246 条，其中 65 条同文件出现多个 FunOpen id，181 条没有可归因的唯一 id。
- 解析仍未完成的 FunOpen 模块：11 个，主要为复杂常量边界/debug 布局；不据此猜映射。

已验证样例：

- `661 req_hero_diff`：`HeroDiffMgr` prototype 8 调用 `HeroCmd.req_hero_diff`，同一管理器唯一门禁为 `TID_FUN_ALL_HERO_DIFF -> 1321`。
- `1312 req_up_rank`：`RoleFigureMgr` prototype 38 在同一 prototype 内先调用 `FunOpenMgr:IsOpen(TID_ROLE_FIGURE_RANK)`，再调用 `RoleCmd.req_up_rank`；映射到 `1051`。
- `16001 req_get_first_recharge_reward`：同一 prototype 直接门禁 `TID_FIRST_RECHARGE -> 1590`。

## access 复核

原启发式把两个明确 setter 误判为 read，现改为 write：

- `21008 req_change_base_info`，客户端请求 `pb_req_guild_base_info`。
- `84410 req_martial_club_set_team_info`，客户端请求 `pb_martial_club_set_team_info_req`。

生成器现在先匹配明确写操作词，再匹配 `_info/_list/get_*` 等读模式。当前 catalog 为 read 90、write 1317。其余仅凭命令名无法证明语义的项保持原保守值，不声称为运行时读写证据。

## 边界

- `same_file_unique` 是管理器级静态关联，不证明 UI 每次调用都必经门禁，因此未加命名吻合的泛命令（如 `fight_start`、`use_box`、背包通用道具）不生成规则。
- 65 个多 id 发送点可能由不同活动阶段、组合条件或调用者决定，未按名称强行择一。
- 11 个解析失败模块及 181 个无唯一 id 发送点仍为 E9-2 证据缺口。
- 本项不包含目标 2 服务端开启路径、在线推送类型或客户端错误码。
