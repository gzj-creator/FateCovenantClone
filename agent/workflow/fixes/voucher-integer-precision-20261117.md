# N3 代金券余额与管理页大整数精度

状态：已修复并通过组件、管理 HTTP 与 SQLite 重开；未部署、未做 APK 真机验收。

## 现象、证据与根因

通用资源支持 int64 数量，但 `voucher-service.mjs::balance` 将券数量先转 Number，再乘 100 分。`9007199254740993` 张会被读成 `9007199254740992` 张；更早的边界是张数仍为安全整数，乘面值后已超出安全范围。管理页 `money` 再转 Number，会再次丢失末位。发放/支付限制使日常小额不触发，但不构成库存累计的精确性证明。

同轮还发现快照的 `redeemed_amount_cents` 直接汇总截断为最近100条的明细，101笔后会少算；累计值应单独遍历全账本，明细展示仍保留100条。

## 修复范围与防复发

金额与张数使用 BigInt 计算；JSON 仍为安全整数时保留 number，超界输出精确十进制字符串；管理页格式化直接消费整数分。支付报价和原有每笔限额不变。新增库存余额、快照 JSON、管理 HTTP、大额格式化、支付扣减和重开库回归。证据存 `analysis/test-runs/numeric-audit-20261117/voucher-precision-*.log`。

## 验证等级与边界

修复后结果：`downstream-after.log` 37/37 通过，覆盖库存余额、快照 JSON、管理 HTTP、大额格式化、支付扣减和重开库；`focused-final.log` 82/82 通过。仅临时库/管理 HTTP 和组件验证，未部署、未改运行库、未操作设备/APK。正常数额 API 字段保持 number；大额消费者必须接受十进制字符串，禁止再无条件转 Number。
