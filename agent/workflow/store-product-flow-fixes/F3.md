# F3 通行证与战令购买

- 状态：组件通过
- 子 agent：f3_permit_purchase
- 最后更新：2026-10-31

## 用户现象

隔离客户端购买通行证后没有界面反应。购买事务实际完成，但通行证页面仍显示可购买；需要在 service 和协议层修复标准通行证，同时复核月卡/战令购买、登录回填、重复购买和已购买状态。

## 调查证据

### 客户端购买事件链

RechargeMgr.ResRechargeSuccess 收到 1900 后依次进入 OnRechargeSuccess、RechargeSuccessFire 和 DispatchRechargeEv，最终触发 RechargeMgr.EVT_RECHARGE。PermitNewMgr.OnRecharge 监听该事件并触发 PermitNewMgr.BUY_PERMIT，通行证主界面、囤货界面和英雄通行证节点再监听 BUY_PERMIT 刷新。

可通过以下命令复核反编译原型：

~~~powershell
node analysis/tools/inspect-lua-focused.mjs RechargeMgr 58
node analysis/tools/inspect-lua-focused.mjs PermitNewMgr 35
node analysis/tools/inspect-lua-focused.mjs FunOpenMgr 42
~~~

关键证据：

- RechargeMgr.DispatchRechargeEv 的 prototype 58 从源文件第 1055 行开始；第 1056–1057 行先创建 extraRetMap = {}，然后直接执行 ipairs(extra_ret_list)，没有 nil/空值保护，直到第 1072 行才触发 EVT_RECHARGE。
- 客户端使用 lua-protobuf，protobuf repeated 字段未上线时解码为 nil。真实日志 analysis/experiments/private-server-20261025/p3/relic-recruit-logcat-full-20261031.txt:414,419 已有同类证据：缺失的 res.extra 在第 62 行进入 ipairs 后报 bad argument #1 to 'ipairs' (table expected, got nil)。
- FunOpenMgr prototype 42 第 627 行先用 ArrayKit.IsEmpty(extra_ret_list) 保护，再到第 628 行执行 ipairs(extra_ret_list)，证明该客户端其他充值事件处理路径明确按“空 repeated 字段可能是 nil”防护。
- RechargeTable.Handle[9] 的配置为 recharge_type=6、lua_module=PermitNewMgr；标准通行证商品正是 RechargeTable.type=6。
- PermitNewMgr.OnRecharge prototype 35 从第 568 行开始，只读取 rechargeCfg.tid，通过 PermitTable.BaseValueIndex.recharge[tid] 或 discount_recharge[tid] 找到通行证，随后 GetPermitInfo、SetHavePay(true)、CheckRedDot()，最后在第 580 行触发 BUY_PERMIT。当前客户端不读取 flag 9 的 payload，但事件触发前必须先安全遍历 extra_ret_list。

真实运行证据：analysis/experiments/private-server-20261025/p3/runtime.local-only.data/events.jsonl:160742-160744 显示商品 191204 已写入 wallet_purchase_committed，并完成 16004 voucher_recharge_committed，但客户端没有产生可见领奖或界面刷新结果。

## 根因

标准通行证的 permit-service.mjs 在购买并更新登录模块 38 的 pb_permit_data.permit_list[].is_pay=true 后，返回了：

~~~js
{ permitId: String(permit.tid), extraRetList: [] }
~~~

wallet 将其编码成空的 res_recharge_success.extra_ret_list=[]。客户端解码后该 repeated 字段为 nil，RechargeMgr.DispatchRechargeEv 在 ipairs(extra_ret_list) 处中断，导致：

1. RechargeMgr.EVT_RECHARGE 未触发；
2. PermitNewMgr.OnRecharge 未执行；
3. PermitNewMgr.BUY_PERMIT 未触发；
4. 已购买页和按钮状态没有立即刷新。

这不是购买未提交，也不是登录模块未更新；根因是 1900 成功回包的 permit handoff 为空。

## 实现

修改 personal-server/game/permit-service.mjs：

- 增加 PERMIT_HANDLE_FLAG=9，注释明确其来源是 RechargeTable.Handle[9] 的 recharge_type=6 -> PermitNewMgr。
- 标准通行证更新模块 38 后返回：
  - extraRetList.length > 0；
  - extra_ret_list[0].flag=9；
  - payload 为更新后的 pb_permit_info，包含通行证 tid 和 is_pay=true。
- pb_permit_info 是当前客户端不会消费的行级 payload；保留它是为了让 flag 与变化行可审计，同时满足客户端不可遍历 nil 的协议约束。

personal-server/game/month-permit-service.mjs 无需修改。现有实现已经：

- 按 ActFrameAct.version 选择匹配的 MonthPermitGear；
- 把商品 id 写入活动登录数据中的 pb_month_permit_info.pay_list；
- 返回 extra_ret_list.flag=116 和更新后的 pb_month_permit_info；
- 在重复 SKU 时返回 307。

wallet 购买主路径已经收集 permit.extraRetList 并编码 1900；gateway 已路由购买链路。因此本任务没有新增 wallet/gateway 共享文件 patch。

## 剩余风险与主 agent 集成项

- 需要主 agent 合并本分支后在隔离客户端购买至少一个标准通行证和一个当前月卡/战令，确认页面立即切换为已购买并保持登录回填；当前不能标记用户视觉通过。
- PermitNewMgr 当前忽略 flag 9 的 data 内容；本次 payload 只用于协议完整性和审计。若后续客户端改为解析该数据，字段来自真实更新后的 pb_permit_info。
- 标准通行证 can_buy_times=0，wallet 在进入 permit handler 前先检查余额。余额不足时重复购买可能先返回 301；余额充足时重复购买返回 307。正常界面应在 flag 9 推送后立即隐藏/禁用购买入口，主 agent 应把该边界纳入临时集成验收。
- flag=9 是基于 RechargeTable.Handle[9] 的静态证据；当前 readGameTables() 未导出 Handle 表，因此 service 使用具名常量并由测试锁定协议行为。
