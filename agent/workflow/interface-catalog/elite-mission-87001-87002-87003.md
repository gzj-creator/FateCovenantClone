## 传输信封

每条 TCP 消息前有 4 字节大端负载长度。握手阶段确定的 flags 决定是否加密，业务实现沿用现有网关，不在这里另定义握手、加密或签名。

请求由 `pb_c2s` 包裹：

```proto
message pb_c2s {
  uint32 seq = 1;   // 客户端请求序号，非零
  sint32 type = 2;  // 87001 / 87002 / 87003
  bytes data = 3;   // 下表的请求 PB；87001/87003 为 ETF 负载，无对应 protobuf schema
  int64 time_ms = 4;
}
```

`type` 使用 `sint32/ZigZag`，`data` 是请求消息的 protobuf wire bytes（87001/87003 除外，见下文）。

成功回包由 `pb_s2c` 包裹：

```proto
message pb_net_err {
  sint32 err = 1;
  bytes vars = 2;
  string stacktrace = 3;
}

message pb_s2c {
  uint32 seq = 1;
  uint32 type = 2;
  bytes data = 3;
  pb_net_err err = 4;
}
```

业务回复必须复用请求的 `seq`，`data` 放对应响应 PB。本仓库当前网关的成功回复写法是只发送 `{seq, data}`，不带 `type`；客户端按非零 `seq` 关联请求。不要假设响应 `type` 等于 87001/87002/87003。`seq=0` 的帧属于推送。

失败回复沿用现有网关模式：省略 `data`，发送 `{seq, err: {err: <code>}}`。上述 `send` 模式见 [`personal-server/game/gateway.mjs`](../../../personal-server/game/gateway.mjs)。

87001 和 87002 的回包都使用下面的 `pb_elite_mission`（DB 协议）：

```proto

  uint64 mission_id = 1;
  bytes boss_bin = 2;        // Boss
  bytes box_award_bin = 3;   //
  pb_mission_difficulty difficulty = 4;
```

| 字段 | tag | 类型 | 重复 | 说明 |
| --- | ---: | --- | --- | --- |

## 共享资源变化结构

87001 回包的 `res` 字段类型为 `pb_res_to_client`，87002 回包的 `res_change` 字段类型为 `pb_res_to_client`：

```proto
message pb_res_to_client {
  repeated pb_res_change changes = 1;
  bool is_overflow = 2;
}

message pb_res_change {
  int64 tid = 1;
  int64 new_num = 2;
  sint64 diff_num = 3;
  bytes new_bin = 4;
  bytes extra = 5;
  pb_res_src src = 6;
}

message pb_res_src {
  int32 src_type = 1;
  int64 src_value = 2;
}
```

回包构造时至少应保证 `changes` 中的 `tid`、`new_num` 和 `diff_num` 与提交后的状态一致。`int64/uint64/sint64` 在仓库现有 codec 的 decode 输出中按字符串处理；构造时不要经过可能丢失精度的 JavaScript `number`。

## 关键字段差异总结

- 87001 请求为 ETF 编码，没有 protobuf 请求 schema；87002 请求为 protobuf；87003 请求为 ETF。
- 87001 回包为 `pb_elite_mission_back`，字段名为 `res`（不是 `res_change`）；87002 回包为 `pb_elite_mission_box_award_back`，字段名为 `res_change`。
- 87001 回包包含 `is_boss`（bool）和 `boss_tid`（uint64）；87002 回包不包含这两个字段，改为 `common_task`（pb_common_task）。
- 87003 请求和回包均为 ETF，没有任何 protobuf schema；具体 wire 形状需运行时证据确认。
- 87001 的 `boss_tid` 为 `uint64`（decode 输出按字符串处理）；87002 的 `box_id_list`/`common_task_id_list` 为 `repeated uint32`。
- `pb_elite_mission` 中的 `mission_id` 为 `uint64`（decode 输出按字符串处理）；`boss_bin`/`box_award_bin` 为 `bytes`，需客户端二次解码。
- 87001 的 `res` 和 87002 的 `res_change` 虽类型相同（`pb_res_to_client`），但字段名不同；实现端必须按回包 schema 的字段名构造。
