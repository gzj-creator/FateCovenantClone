## 传输信封

每条 TCP 消息前有 4 字节大端负载长度。握手阶段确定的 flags 决定是否加密，业务实现沿用现有网关，不在这里另定义握手、加密或签名。

请求由 `pb_c2s` 包裹：

```proto
message pb_c2s {
  uint32 seq = 1;   // 客户端请求序号，非零
  sint32 type = 2;  // 1208
  bytes data = 3;   // ETF 负载；当前静态证据中无对应 protobuf 请求 schema
  int64 time_ms = 4;
}
```

`type` 使用 `sint32/ZigZag`，`data` 是请求消息的 protobuf wire bytes（本接口为 ETF，见下文）。

成功回包由 `pb_s2c` 包裹：

```proto
message pb_net_err {
  sint32 err = 1;
  bytes vars = 2;
  string stacktrace = 3;
}

message pb_s2c {
  uint32 seq = 1;
  uint32 type = 2;
  bytes data = 3;
  pb_net_err err = 4;
}
```

业务回复必须复用请求的 `seq`，`data` 放对应响应 PB。本仓库当前网关的成功回复写法是只发送 `{seq, data}`，不带 `type`；客户端按非零 `seq` 关联请求。不要假设响应 `type` 等于 1208。`seq=0` 的帧属于推送。

失败回复沿用现有网关模式：省略 `data`，发送 `{seq, err: {err: <code>}}`。上述 `send` 模式见 [`personal-server/game/gateway.mjs`](../../../personal-server/game/gateway.mjs)。

## type 1208：商店刷新

请求：当前静态证据中 `req_refresh_shop` 的请求编码为 ETF，`static-schemas.json` 中没有对应的 protobuf 请求 schema（`request.schema = null`）。Lua 编码器入口为 `ShopCmd.req_refresh_shop`，符号追踪显示单个输入寄存器（register 0）被直接作为 ETF 参数写入请求。具体 ETF 元组/列表形状、字段含义和合法取值范围仍需运行时证据确认；实现端不能仅凭字段名假设其语义。静态证据未显示额外的 shop_id / cell_index 等参数，刷新目标可能由客户端当前打开的商店上下文决定，但这一点尚未通过运行时验证。

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `param`（ETF 位置参数） | - | ETF/未确定 | - | 静态追踪仅显示单个输入寄存器；protobuf schema 不存在，字段名、tag、类型均未确定 |

请求对象形状（仅表示调用入口，不定义合法数值）：

```json
{
  "param": 0
}
```

上例只表示调用入口形状，示例数值不代表合法游戏数据，且 ETF 的实际 wire 形状尚未确认。

回包消息：

```proto
message pb_manual_refresh_shop_back {
  pb_shop_info shop = 1;
  pb_res_to_client res = 2;
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `shop` | 1 | `pb_shop_info` | 否 | 刷新后的商店信息（含商品分组与版本号） |
| `res` | 2 | `pb_res_to_client` | 否 | 本次刷新造成的资源变化（注意字段名为 `res`，不是 `res_change` / `res_to_client`） |

注意：1208 回包的资源字段名为单数 `res`，与其它商店回包命名不同：`pb_mystery_shop_manual_refresh_back` 使用 `res_change`，`pb_shop_assistant_buy_back` 使用 `res_to_client`。实现端必须按 `pb_manual_refresh_shop_back.res` 解析，不能复用其它消息的字段名。

## 共享商店结构

回包使用的 `pb_shop_info` 及其嵌套结构定义如下：

```proto
message pb_shop_info {
  int32 id = 1;
  repeated pb_shop_items_group items_groups = 2;
  int32 version = 3;
}

message pb_shop_items_group {
  repeated pb_shop_item_info item_list = 1;
  bytes group_data_bin = 2;
}

message pb_shop_item_info {
  int64 tid = 2;       // 注意：无 tag 1 字段
  int32 buy_count = 3;
}

message pb_shop_manual_refresh {
  int32 last_refresh_time = 1;
  int32 next_free_count_time = 2;
  int32 free_refresh_count = 3;
  int32 pay_refresh_count = 4;
  int32 all_refresh_count = 5;
  int64 last_auto_refresh_time = 6;
  int64 privilege_used_times = 7;
}
```

| 字段 | tag | 类型 | 重复 | 说明 |
| --- | ---: | --- | --- | --- |
| `pb_shop_info.id` | 1 | `int32` | 否 | 商店 id |
| `pb_shop_info.items_groups` | 2 | `pb_shop_items_group` | 是 | 商品分组列表 |
| `pb_shop_info.version` | 3 | `int32` | 否 | 商店版本号，客户端据此判断是否需要全量同步 |
| `pb_shop_items_group.item_list` | 1 | `pb_shop_item_info` | 是 | 该分组下的商品列表 |
| `pb_shop_items_group.group_data_bin` | 2 | `bytes` | 否 | 分组附加二进制数据（语义未在 proto 中注释） |
| `pb_shop_item_info.tid` | 2 | `int64` | 否 | 商品模板 id；`int64` 在 codec decode 输出中按字符串处理 |
| `pb_shop_item_info.buy_count` | 3 | `int32` | 否 | 已购买数量 |
| `pb_shop_manual_refresh.last_refresh_time` | 1 | `int32` | 否 | 上次手动刷新时间 |
| `pb_shop_manual_refresh.next_free_count_time` | 2 | `int32` | 否 | 下次免费刷新计数时间 |
| `pb_shop_manual_refresh.free_refresh_count` | 3 | `int32` | 否 | 免费刷新次数 |
| `pb_shop_manual_refresh.pay_refresh_count` | 4 | `int32` | 否 | 付费刷新次数 |
| `pb_shop_manual_refresh.all_refresh_count` | 5 | `int32` | 否 | 总刷新次数 |
| `pb_shop_manual_refresh.last_auto_refresh_time` | 6 | `int64` | 否 | 上次自动刷新时间；`int64` 按字符串处理 |
| `pb_shop_manual_refresh.privilege_used_times` | 7 | `int64` | 否 | 特权已使用次数；`int64` 按字符串处理 |

注意：`pb_shop_item_info` 没有 tag 1 字段（从 tag 2 开始）。`pb_shop_manual_refresh` 未直接嵌套在 `pb_shop_info` 中，但属于同一商店域的刷新元数据，实现端若需同步刷新计数应单独维护或通过其它接口获取；当前 1208 回包仅返回 `shop` 与 `res`。

## 共享资源变化结构

```proto
message pb_res_to_client {
  repeated pb_res_change changes = 1;
  bool is_overflow = 2;
}

message pb_res_change {
  int64 tid = 1;
  int64 new_num = 2;
  sint64 diff_num = 3;
  bytes new_bin = 4;
  bytes extra = 5;
  pb_res_src src = 6;
}

message pb_res_src {
  int32 src_type = 1;
  int64 src_value = 2;
}
```

| 字段 | tag | 类型 | 重复 | 说明 |
| --- | ---: | --- | --- | --- |
| `pb_res_to_client.changes` | 1 | `pb_res_change` | 是 | 资源变化列表 |
| `pb_res_to_client.is_overflow` | 2 | `bool` | 否 | 是否溢出 |
| `pb_res_change.tid` | 1 | `int64` | 否 | 资源模板 id；按字符串处理 |
| `pb_res_change.new_num` | 2 | `int64` | 否 | 变化后数量；按字符串处理 |
| `pb_res_change.diff_num` | 3 | `sint64` | 否 | 变化量（ZigZag）；按字符串处理 |
| `pb_res_change.new_bin` | 4 | `bytes` | 否 | 新二进制数据 |
| `pb_res_change.extra` | 5 | `bytes` | 否 | 附加数据 |
| `pb_res_change.src` | 6 | `pb_res_src` | 否 | 变化来源 |
| `pb_res_src.src_type` | 1 | `int32` | 否 | 来源类型 |
| `pb_res_src.src_value` | 2 | `int64` | 否 | 来源值；按字符串处理 |

回包构造时至少应保证 `changes` 中的 `tid`、`new_num` 和 `diff_num` 与提交后的状态一致。`int64/uint64/sint64` 在仓库现有 codec 的 decode 输出中按字符串处理；构造时不要经过可能丢失精度的 JavaScript `number`。

## 实现交接约束

- 使用仓库现有 `personal-server/protocol/game-codec.mjs` 的 `codec.pack(schemaName, object)` / `codec.unpack(schemaName, bytes)`，保留 proto 的 snake_case 字段名。
- 1208 请求为 ETF，无 protobuf 请求 schema；响应使用 `pb_manual_refresh_shop_back`。
- 响应字段为 `shop`（`pb_shop_info`）与 `res`（`pb_res_to_client`）；注意资源字段名为 `res`。
- 成功回包复用请求 `seq`；当前本机服实现的业务回复不设置 `pb_s2c.type`。
- 该接口当前只有静态契约，不能标记为“已捕获”“已解码回包”或“已操作验收”，除非后续提供对应运行时证据。
