本文面向接口实现，给出 `1001`、`1002`、`1006` 的请求和回包参数。字段定义、tag、类型和调用侧编码均已从当前客户端静态产物核对；这三个接口尚无实观请求/回包，也没有运行时状态变更或客户端操作验收。

## 传输信封

每条 TCP 消息前有 4 字节大端负载长度。握手阶段确定的 flags 决定是否加密，业务实现沿用现有网关，不在这里另定义握手、加密或签名。

请求由 `pb_c2s` 包裹：

```proto
message pb_c2s {
  uint32 seq = 1;   // 客户端请求序号，非零
  sint32 type = 2;  // 1001 / 1002 / 1006
  bytes data = 3;   // 下表的请求 PB
  int64 time_ms = 4;
}
```

`type` 使用 `sint32/ZigZag`，`data` 是请求消息的 protobuf wire bytes。

成功回包由 `pb_s2c` 包裹：

```proto
message pb_net_err {
  sint32 err = 1;
  bytes vars = 2;
  string stacktrace = 3;
}

message pb_s2c {
  uint32 seq = 1;
  uint32 type = 2;
  bytes data = 3;
  pb_net_err err = 4;
}
```

业务回复必须复用请求的 `seq`，`data` 放对应响应 PB。本仓库当前网关的成功回复写法是只发送 `{seq, data}`，不带 `type`；客户端按非零 `seq` 关联请求。不要假设响应 `type` 等于 1001/1002/1006。`seq=0` 的帧属于推送。

失败回复沿用现有网关模式：省略 `data`，发送 `{seq, err: {err: <code>}}`。上述 `send` 模式见 [`personal-server/game/gateway.mjs`](../../../personal-server/game/gateway.mjs)。

## type 1001：装备升级

请求消息：

```proto
message pb_equip_level_up_req {
  repeated pb_equip_level_up_equip equips = 1;
}

message pb_equip_level_up_equip {
  uint32 id = 1;         // 强化装备 id
  uint32 add_level = 2;  // 强化的等级增量
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `equips` | 1 | `pb_equip_level_up_equip` | 是 | 本批升级项 |
| `equips[].id` | 1 | `uint32` | 否 | 装备实例 id |
| `equips[].add_level` | 2 | `uint32` | 否 | 本次增加等级；字段不是 `target_level` |

请求对象形状：

```json
{
  "equips": [
    { "id": 0, "add_level": 0 }
  ]
}
```

上例只表示字段形状，示例数值不代表合法游戏数据。`EquipCmd` 的 Lua 编码器直接把输入表的 `equips` 字段写入请求 PB；当前 `EquipMgr.prototype[13]` 也把 `equips` 原样交给该调用。

回包消息：

```proto
message pb_equip_level_up_rsp {
  repeated pb_equip equips = 1;
  pb_res_to_client res_change = 2;
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `equips` | 1 | `pb_equip` | 是 | 升级后需要同步给客户端的装备记录 |
| `res_change` | 2 | `pb_res_to_client` | 否 | 本次消耗/返还等资源变化 |

## type 1002：装备锻造

请求消息：

```proto
message pb_equip_forge_req {
  repeated pb_equip_forge_one equips = 1;
  bool is_one_key = 2;
}

message pb_equip_forge_one {
  uint32 index = 1;     // 养成格子索引
  uint32 equip_id = 2;  // 装备 id
  uint32 times = 3;     // 打造次数
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `equips` | 1 | `pb_equip_forge_one` | 是 | 本批锻造项 |
| `equips[].index` | 1 | `uint32` | 否 | 养成格子索引 |
| `equips[].equip_id` | 2 | `uint32` | 否 | 装备 id |
| `equips[].times` | 3 | `uint32` | 否 | 打造次数 |
| `is_one_key` | 2 | `bool` | 否 | 是否一键打造；缺省值为 `false` |

请求对象形状：

```json
{
  "equips": [
    { "index": 0, "equip_id": 0, "times": 0 }
  ],
  "is_one_key": true
}
```

上例只表示字段形状，不定义合法索引、装备或次数。当前 `EquipMgr.prototype[16]` 先通过 `EquipUtils.ConvertCellAndIdxToPb(cell, idx)` 生成锻造项，再调用 `req_equip_forge`，该 UI 调用点传入 `is_one_key=true`。即使一键打造，请求字段仍叫 `repeated equips`。

回包消息：

```proto
message pb_equip_forge_rsp {
  pb_res_to_client res_change = 1;
  repeated pb_equip equip = 2;
  repeated pb_lineup change_lineup = 3;
  pb_pre_lineup cur_pre_lineup = 4;
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `res_change` | 1 | `pb_res_to_client` | 否 | 锻造造成的资源变化 |
| `equip` | 2 | `pb_equip` | 是 | 锻造得到的装备记录 |
| `change_lineup` | 3 | `pb_lineup` | 是 | 因属性/战力变化而需要同步的编队 |
| `cur_pre_lineup` | 4 | `pb_pre_lineup` | 否 | 当前预设队伍 |

注意：1002 回包字段名是单数 `equip`，但它是 `repeated`。不要按请求字段名写成 `equips`。

## type 1006：装备穿戴

请求消息：

```proto
message pb_equip_wear_req {
  repeated pb_equip_wear wears = 1;
}

message pb_equip_wear {
  uint32 index = 1;
  uint32 id = 2;
  uint32 tid = 3;
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `wears` | 1 | `pb_equip_wear` | 是 | 本批穿戴项 |
| `wears[].index` | 1 | `uint32` | 否 | 客户端索引字段；proto 无语义注释 |
| `wears[].id` | 2 | `uint32` | 否 | 客户端 id 字段；proto 无语义注释 |
| `wears[].tid` | 3 | `uint32` | 否 | 客户端 tid 字段；proto 无语义注释 |

请求对象形状：

```json
{
  "wears": [
    { "index": 0, "id": 0, "tid": 0 }
  ]
}
```

上例只表示字段形状。当前 `EquipCmd.req_equip_wear` 直接把输入表赋给 `pb_equip_wear_req.wears`；静态证据没有给出三个数值字段的业务注释，也没有关联到一次已验收的穿戴操作。实现端应结合现有装备/编队状态模型解释 `index/id/tid`，不能仅凭字段名把它们当作已证实的角色槽位或模板 id。

回包消息：

```proto
message pb_equip_wear_rsp {
  pb_res_to_client res_change = 1;
  repeated pb_equip equips = 2;
  repeated pb_lineup change_lineup = 3;
  pb_pre_lineup cur_pre_lineup = 4;
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `res_change` | 1 | `pb_res_to_client` | 否 | 穿戴造成的资源变化 |
| `equips` | 2 | `pb_equip` | 是 | 发生变化的装备记录 |
| `change_lineup` | 3 | `pb_lineup` | 是 | 发生变化的编队 |
| `cur_pre_lineup` | 4 | `pb_pre_lineup` | 否 | 当前预设队伍 |

注意：1006 的 repeated 回包字段是复数 `equips`；这与 1002 的 `equip` 不同。

## 共享装备结构

三个回包都可能使用下面的 `pb_equip`：

```proto
message pb_equip {
  uint32 id = 1;
  uint32 tid = 2;
  uint32 level = 3;
  uint32 level_exp = 4;
  uint32 inscription = 5;
  uint32 refine = 6;
  uint32 refine_exp = 7;
  repeated pb_res_obj random_develop_cost = 8;
}

message pb_res_obj {
  int64 tid = 1;
  int64 num = 2;
}
```

| 字段 | tag | 类型 | 重复 | 说明 |
| --- | ---: | --- | --- | --- |
| `id` | 1 | `uint32` | 否 | 装备实例 id |
| `tid` | 2 | `uint32` | 否 | 装备模板 id |
| `level` | 3 | `uint32` | 否 | 当前等级 |
| `level_exp` | 4 | `uint32` | 否 | 当前等级经验 |
| `inscription` | 5 | `uint32` | 否 | 铭刻值 |
| `refine` | 6 | `uint32` | 否 | 精炼等级 |
| `refine_exp` | 7 | `uint32` | 否 | 精炼经验 |
| `random_develop_cost` | 8 | `pb_res_obj` | 是 | 随机养成消耗列表 |

## 共享资源变化结构

```proto
message pb_res_to_client {
  repeated pb_res_change changes = 1;
  bool is_overflow = 2;
}

message pb_res_change {
  int64 tid = 1;
  int64 new_num = 2;
  sint64 diff_num = 3;
  bytes new_bin = 4;
  bytes extra = 5;
  pb_res_src src = 6;
}

message pb_res_src {
  int32 src_type = 1;
  int64 src_value = 2;
}
```

回包构造时至少应保证 `changes` 中的 `tid`、`new_num` 和 `diff_num` 与提交后的状态一致。`int64/uint64/sint64` 在仓库现有 codec 的 decode 输出中按字符串处理；构造时不要经过可能丢失精度的 JavaScript `number`。

## 回包编队结构

1002 和 1006 的 `change_lineup` 使用 `pb_lineup`，`cur_pre_lineup` 使用 `pb_pre_lineup`：

```proto
message pb_lineup {
  int32 type = 1;
  repeated pb_lineup_team team_list = 2;
  repeated pb_lineup_custom_attr custom_attr = 3;
  int32 custom_lineup_index = 4;
  int32 select_camp = 5;
}

message pb_pre_lineup {
  uint32 index = 1;
  pb_lineup_team lineup = 2;
  int32 select_camp = 3;
}

message pb_lineup_team {
  int32 team_id = 1;
  uint64 max_power = 2;
  repeated pb_lineup_fighter fighter_list = 3;
  repeated int32 artifact_list = 4;
  uint64 power = 5;
  repeated pb_lineup_lease_fighter lease_fighter_list = 6;
  repeated uint32 pet_list = 7;
  repeated uint64 elves_list = 8;
  repeated pb_lease_unit lease_pet = 9;
  repeated pb_lease_unit lease_elves = 10;
  repeated pb_lease_unit lease_artifact = 11;
}

message pb_lineup_fighter {
  uint32 loc = 1;
  uint32 index = 2;
  uint64 hero_id = 3;
  repeated uint32 equip_ids = 4;
  uint64 power = 5;
  uint32 fetter_tid = 6;
  repeated uint64 relic_ids = 7;
}

message pb_lineup_custom_attr {
  uint32 type = 1;
  bytes value = 2;
}
```

`pb_lineup_lease_fighter`、`pb_lease_hero` 和 `pb_lease_unit` 的完整字段见 [static-schemas.json](static-schemas.json)；实现这三个装备接口时通常只需回填实际发生变化的编队，不要伪造无关租借数据。

## 实现交接约束

- 使用仓库现有 `personal-server/protocol/game-codec.mjs` 的 `codec.pack(schemaName, object)` / `codec.unpack(schemaName, bytes)`，保留 proto 的 snake_case 字段名。
- 1001 请求和回包字段均为 `equips`。
- 1002 请求字段为 `equips`，回包装备字段为 `equip`。
- 1006 请求字段为 `wears`，回包字段为 `equips`。
- 成功回包复用请求 `seq`；当前本机服实现的业务回复不设置 `pb_s2c.type`。
- 三个接口当前都只有静态契约，不能标记为“已捕获”“已解码回包”或“已操作验收”，除非后续提供对应运行时证据。
