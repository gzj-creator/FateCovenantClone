## 传输信封

每条 TCP 消息前有 4 字节大端负载长度。握手阶段确定的 flags 决定是否加密，业务实现沿用现有网关，不在这里另定义握手、加密或签名。

请求由 `pb_c2s` 包裹：

```proto
message pb_c2s {
  uint32 seq = 1;   // 客户端请求序号，非零
  sint32 type = 2;  // 37062 / 37071
  bytes data = 3;   // ETF 编码的单参数（见下）
  int64 time_ms = 4;
}
```

`type` 使用 `sint32/ZigZag`。与 37060/37061/37070 不同，这两个接口的请求 **不是** protobuf，而是 `EncodeErl`（Erlang 项）编码的单个位置参数；`data` 为该 Erlang 项的 wire bytes，没有对应的 protobuf 请求消息。

成功回包由 `pb_s2c` 包裹：

```proto
message pb_net_err {
  sint32 err = 1;
  bytes vars = 2;
  string stacktrace = 3;
}

message pb_s2c {
  uint32 seq = 1;
  uint32 type = 2;
  bytes data = 3;
  pb_net_err err = 4;
}
```

业务回复必须复用请求的 `seq`，`data` 放对应响应 PB。本仓库当前网关的成功回复写法是只发送 `{seq, data}`，不带 `type`；客户端按非零 `seq` 关联请求。不要假设响应 `type` 等于 37062/37071。`seq=0` 的帧属于推送。

失败回复沿用现有网关模式：省略 `data`，发送 `{seq, err: {err: <code>}}`。上述 `send` 模式见 [`personal-server/game/gateway.mjs`](../../../personal-server/game/gateway.mjs)。

## type 37062：圣器品质提升

请求消息：

- 编码方式为 `EncodeErl`（Erlang 项），**不是** protobuf。静态证据只显示单个位置参数（register 0），未解析为具名字段；`ArtifactMgr` 调用点传入 `tid`。客户端调用 `ArtifactCmd.req_artifact_quality(tid)` 时把该值作为 Erlang 项直接发送。
- 无法从静态产物确认该参数的标量类型（整数/索引），也未确认是否为 `uint32`/`int64`。实现端应按客户端传入的单个整数 tid 处理，并在运行时验证。

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| (Erlang 项) | - | 未知标量 | 否 | 圣器 tid；proto 无对应请求消息 |

回包消息：

```proto
message pb_artifact_back {
  pb_res_to_client res = 1;       // 资源信息
  pb_artifact artifact = 2;       // 神器信息
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `res` | 1 | `pb_res_to_client` | 否 | 本次消耗/返还等资源变化 |
| `artifact` | 2 | `pb_artifact` | 否 | 品质提升后的圣器完整记录 |

注意：37062 的回包复用 `pb_artifact_back`，与 37060/37061 的回包相同，字段为 `res` + `artifact`。

## 共享圣器结构

两个回包都使用 [artifact-37060-37061-37070.md](artifact-37060-37061-37070.md) 中已定义的 `pb_artifact` 与 `pb_res_to_client`，此处引用而不重复定义。关键字段如下（完整定义见该文档）：

`pb_artifact`：
- `tid` (1, `int64`) — 圣器模板 id；decode 输出按字符串处理
- `num` (2, `int32`) — 数量
- `star` (3, `int32`) — 星级
- `star_node` (4, `int32`) — 星节点
- `forge_list` (5, `uint32`, repeated) — 神锻列表
- `stage` (6, `uint32`) — 阶段
- `quality` (7, `int32`) — 品质
- `level` (8, `int32`) — 当前等级
- `break_level` (9, `int32`) — 突破等级
- `is_fly_up` (10, `bool`) — 是否飞升
- `artifact_skin` (11, `int32`) — 圣器皮肤

`pb_res_to_client` / `pb_res_change` / `pb_res_src` 的完整定义见 [artifact-37060-37061-37070.md](artifact-37060-37061-37070.md)。

## 关键字段差异

- 37062 与 37071 的请求都不是 protobuf，而是 `EncodeErl` 单参数；与 37060/37061/37070 的 protobuf 请求不同，实现端不能用 `codec.pack` 处理请求，需走 ETF 编码路径。
- 37062 的回包复用 `pb_artifact_back`，资源字段名为 `res`；37071 的回包使用 `pb_artifact_break_level_up_rsp`，资源字段名为 `res_change`。实现时不要混用。
- 37062/37071 的请求参数均为单个 Erlang 项，静态证据无法确认标量类型；与 lineup 210/217 的 ETF 单参数情况相同。
- `pb_artifact.tid` 为 `int64`（decode 为字符串），而请求 ETF 参数的 tid 类型未确认；两者语义相关但编码不同，不要直接等同。
- `pb_artifact.quality` (tag 7) 与 `pb_artifact.break_level` (tag 9) 分别对应这两个接口的核心养成字段；品质提升应更新 `quality`，突破应更新 `break_level`。

## 实现交接约束

- 请求使用 ETF 编码（无 protobuf schema），响应使用 protobuf 编解码；使用仓库现有 `personal-server/protocol/game-codec.mjs` 的 `codec.pack(schemaName, object)` / `codec.unpack(schemaName, bytes)` 处理响应，保留 proto 的 snake_case 字段名。
- 37062 回包 schema 为 `pb_artifact_back`（字段 `res` + `artifact`）。
- 37071 回包 schema 为 `pb_artifact_break_level_up_rsp`（字段 `res_change` + `artifact`）。
- 成功回包复用请求 `seq`；当前本机服实现的业务回复不设置 `pb_s2c.type`。
- `int64/uint64/sint64` 的 decode 输出按字符串处理；构造时不要经过可能丢失精度的 JavaScript `number`。
- 两个接口当前都只有静态契约，不能标记为“已捕获”“已解码回包”或“已操作验收”，除非后续提供对应运行时证据。
- 当前没有实观请求/回包或客户端操作验收；所有字段语义仍需运行时验证。请求 ETF 参数的标量类型与准确值形状需在捕获运行时流量后确认。
