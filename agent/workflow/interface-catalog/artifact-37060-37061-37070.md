## 传输信封

每条 TCP 消息前有 4 字节大端负载长度。握手阶段确定的 flags 决定是否加密，业务实现沿用现有网关，不在这里另定义握手、加密或签名。

请求由 `pb_c2s` 包裹：

```proto
message pb_c2s {
  uint32 seq = 1;   // 客户端请求序号，非零
  sint32 type = 2;  // 37060 / 37061 / 37070
  bytes data = 3;   // 下表的请求 PB
  int64 time_ms = 4;
}
```

`type` 使用 `sint32/ZigZag`，`data` 是请求消息的 protobuf wire bytes。

成功回包由 `pb_s2c` 包裹：

```proto
message pb_net_err {
  sint32 err = 1;
  bytes vars = 2;
  string stacktrace = 3;
}

message pb_s2c {
  uint32 seq = 1;
  uint32 type = 2;
  bytes data = 3;
  pb_net_err err = 4;
}
```

业务回复必须复用请求的 `seq`，`data` 放对应响应 PB。本仓库当前网关的成功回复写法是只发送 `{seq, data}`，不带 `type`；客户端按非零 `seq` 关联请求。不要假设响应 `type` 等于 37060/37061/37070。`seq=0` 的帧属于推送。

失败回复沿用现有网关模式：省略 `data`，发送 `{seq, err: {err: <code>}}`。上述 `send` 模式见 [`personal-server/game/gateway.mjs`](../../../personal-server/game/gateway.mjs)。

## type 37060：圣器合成（升星）

请求消息：

```proto
message pb_artifact_star_up_req {
  uint32 tid = 1;     // 圣约tid
  uint32 times = 2;   // 升星次数
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `tid` | 1 | `uint32` | 否 | 圣器模板 tid |
| `times` | 2 | `uint32` | 否 | 本次升星次数 |

请求对象形状：

```json
{
  "tid": 0,
  "times": 0
}
```

上例只表示字段形状，示例数值不代表合法游戏数据。`ArtifactCmd` 的 Lua 编码器直接把输入的 `tid`、`times` 写入请求 PB。

回包消息：

```proto
message pb_artifact_back {
  pb_res_to_client res = 1;       // 资源信息
  pb_artifact artifact = 2;       // 神器信息
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `res` | 1 | `pb_res_to_client` | 否 | 本次消耗/返还等资源变化 |
| `artifact` | 2 | `pb_artifact` | 否 | 合成/升星后的圣器完整记录 |

## type 37061：圣器强化（神锻）

请求消息：

```proto
message pb_req_artifact_forge {
  int64 tid = 1;          // 神锻id

message pb_req_artifact_forge_one {
  int32 type = 1;    // 神锻类型
  int32 forge_count = 2;  // 神锻次数
```

| 路径 | tag | 类型 | 重复 | 参数 |


```proto
message pb_artifact {
  int64 tid = 1;
  int32 num = 2;
  int32 star = 3;
  int32 star_node = 4;
  repeated uint32 forge_list = 5;
  uint32 stage = 6;
  int32 quality = 7;
  int32 level = 8;
  int32 break_level = 9;
```

## 共享资源变化结构

```proto
message pb_res_to_client {
  repeated pb_res_change changes = 1;
  bool is_overflow = 2;
}

message pb_res_change {
  int64 tid = 1;
  int64 new_num = 2;
  sint64 diff_num = 3;
  bytes new_bin = 4;
  bytes extra = 5;
  pb_res_src src = 6;
}

message pb_res_src {
  int32 src_type = 1;
  int64 src_value = 2;
}
```

回包构造时至少应保证 `changes` 中的 `tid`、`new_num` 和 `diff_num` 与提交后的状态一致。`int64/uint64/sint64` 在仓库现有 codec 的 decode 输出中按字符串处理；构造时不要经过可能丢失精度的 JavaScript `number`。

## 关键字段差异

- 37060 与 37070 的请求都使用 `uint32 tid` + `uint32 times`，但 schema 名不同：37060 为 `pb_artifact_star_up_req`，37070 为 `pb_artifact_level_up_req`。
- 37061 的请求使用 `int64 tid`（decode 为字符串）和 `repeated forge_list`，每个子项为 `{type, forge_count}`，不是简单的 `times`。
- 37060 与 37061 的回包都复用 `pb_artifact_back`，字段为 `res` + `artifact`；37070 的回包使用 `pb_artifact_level_up_rsp`，字段为 `res_change` + `artifact`。
- 37060/37061 的资源变化字段名是 `res`，37070 是 `res_change`；实现时不要混用。
- `pb_artifact.tid` 为 `int64`，而请求 37060/37070 的 `tid` 为 `uint32`；两者语义不同，不要直接等同。

## 实现交接约束

- 使用仓库现有 `personal-server/protocol/game-codec.mjs` 的 `codec.pack(schemaName, object)` / `codec.unpack(schemaName, bytes)`，保留 proto 的 snake_case 字段名。
- 成功回包复用请求 `seq`；当前本机服实现的业务回复不设置 `pb_s2c.type`。
- 三个接口当前都只有静态契约，不能标记为“已捕获”“已解码回包”或“已操作验收”，除非后续提供对应运行时证据。
- `int64/uint64/sint64` 的 decode 输出按字符串处理。
- `forge_list` 字段是单数语义但 repeated，已特别标注。
