## 传输信封

每条 TCP 消息前有 4 字节大端负载长度。握手阶段确定的 flags 决定是否加密，业务实现沿用现有网关，不在这里另定义握手、加密或签名。

请求由 `pb_c2s` 包裹：

```proto
message pb_c2s {
  uint32 seq = 1;   // 客户端请求序号，非零
  sint32 type = 2;  // 1003 / 1004 / 1005
  bytes data = 3;   // 下表的请求 PB，或 1003 的 ETF 参数
  int64 time_ms = 4;
}
```

`type` 使用 `sint32/ZigZag`，`data` 是请求消息的 protobuf wire bytes；1003 的请求编码为 `etf`，没有对应 proto 请求消息。

成功回包由 `pb_s2c` 包裹：

```proto
message pb_net_err {
  sint32 err = 1;
  bytes vars = 2;
  string stacktrace = 3;
}

message pb_s2c {
  uint32 seq = 1;
  uint32 type = 2;
  bytes data = 3;
  pb_net_err err = 4;
}
```

业务回复必须复用请求的 `seq`，`data` 放对应响应 PB。本仓库当前网关的成功回复写法是只发送 `{seq, data}`，不带 `type`；客户端按非零 `seq` 关联请求。不要假设响应 `type` 等于 1003/1004/1005。`seq=0` 的帧属于推送。

失败回复沿用现有网关模式：省略 `data`，发送 `{seq, err: {err: <code>}}`。上述 `send` 模式见 [`personal-server/game/gateway.mjs`](../../../personal-server/game/gateway.mjs)。

## type 1003：装备精炼

请求：静态证据中该接口的请求编码为 `etf`，`schema=null`，仅有一个输入寄存器（`input-register 0`），没有 `pb_equip_refine_req` 消息。实现时不能按 protobuf 请求消息解码；应沿用客户端 `EquipCmd.req_equip_refine` 的 Erl 参数约定，并结合现有服务端状态模型确定入参。

回包消息：

```proto
message pb_equip_refine_rsp {
  pb_equip equip = 1;
  uint32 multi = 2;
  pb_res_to_client res_change = 3;
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `equip` | 1 | `pb_equip` | 否 | 精炼后的装备记录 |
| `multi` | 2 | `uint32` | 否 | 精炼倍率 |
| `res_change` | 3 | `pb_res_to_client` | 否 | 本次消耗/返还等资源变化 |

注意：1003 回包的 `equip` 是单个对象，不是 `repeated`；这与 1002 的 `equip`（repeated）和 1006 的 `equips`（repeated）不同。`multi` 也是单值，不是数组。

## type 1004：装备一键精炼

请求消息：

```proto
message pb_equip_refine_one_key_req {
  uint32 equip_id = 1;     // 装备id
  uint32 target_level = 2; // 目标等级
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `equip_id` | 1 | `uint32` | 否 | 装备实例 id |
| `target_level` | 2 | `uint32` | 否 | 目标精炼等级 |

请求对象形状：

```json
{
  "equip_id": 0,
  "target_level": 0
}
```

上例只表示字段形状，示例数值不代表合法游戏数据。`EquipCmd.req_equip_refine_one_key` 将 `equip_id`、`target_level` 两个输入寄存器写入请求 PB。

回包消息：

```proto
message pb_equip_refine_one_key_rsp {
  pb_equip equip = 1;               // 新装备
  pb_res_to_client res_change = 2;  // 资源变化
  repeated uint32 multi = 3;        // 倍率
  uint32 times = 4;                 // 精炼次数
}
```

| 路径 | tag | 类型 | 重复 | 参数 |
| --- | ---: | --- | --- | --- |
| `equip` | 1 | `pb_equip` | 否 | 精炼后的装备记录 |
| `res_change` | 2 | `pb_res_to_client` | 否 | 本次消耗/返还等资源变化 |
| `multi` | 3 | `uint32` | 是 | 倍率列表；字段名是单数，但它是 `repeated` |
| `times` | 4 | `uint32` | 否 | 本次精炼次数 |

注意：`multi` 字段名是单数 `multi`，但它是 `repeated uint32`。实现和解码时必须按数组处理，不能按单值处理。

## 共享装备结构

三个回包都使用下面的 `pb_equip`，完整定义见 [equipment-1001-1002-1006.md](equipment-1001-1002-1006.md)：

```proto
message pb_equip {
  uint32 id = 1;
  uint32 tid = 2;
  uint32 level = 3;
  uint32 level_exp = 4;
  uint32 inscription = 5;
  uint32 refine = 6;
  uint32 refine_exp = 7;
  repeated pb_res_obj random_develop_cost = 8;
}

message pb_res_obj {
  int64 tid = 1;
  int64 num = 2;
}
```

| 字段 | tag | 类型 | 重复 | 说明 |
| --- | ---: | --- | --- | --- |
| `id` | 1 | `uint32` | 否 | 装备实例 id |
| `tid` | 2 | `uint32` | 否 | 装备模板 id |
| `level` | 3 | `uint32` | 否 | 当前等级 |
| `level_exp` | 4 | `uint32` | 否 | 当前等级经验 |
| `inscription` | 5 | `uint32` | 否 | 铭刻值 |
| `refine` | 6 | `uint32` | 否 | 精炼等级 |
| `refine_exp` | 7 | `uint32` | 否 | 精炼经验 |
| `random_develop_cost` | 8 | `pb_res_obj` | 是 | 随机养成消耗列表 |

## 共享资源变化结构

```proto
message pb_res_to_client {
  repeated pb_res_change changes = 1;
  bool is_overflow = 2;
}

message pb_res_change {
  int64 tid = 1;
  int64 new_num = 2;
  sint64 diff_num = 3;
  bytes new_bin = 4;
  bytes extra = 5;
  pb_res_src src = 6;
}

message pb_res_src {
  int32 src_type = 1;
  int64 src_value = 2;
}
```

回包构造时至少应保证 `changes` 中的 `tid`、`new_num` 和 `diff_num` 与提交后的状态一致。`int64/uint64/sint64` 在仓库现有 codec 的 decode 输出中按字符串处理；构造时不要经过可能丢失精度的 JavaScript `number`。

## 回包编队结构

本组三个接口的回包都不包含 `change_lineup` / `cur_pre_lineup`；编队同步仅在 1002 和 1006 中出现。完整 `pb_lineup`、`pb_pre_lineup` 等定义见 [equipment-1001-1002-1006.md](equipment-1001-1002-1006.md)。

## 实现交接约束

- 使用仓库现有 `personal-server/protocol/game-codec.mjs` 的 `codec.pack(schemaName, object)` / `codec.unpack(schemaName, bytes)`，保留 proto 的 snake_case 字段名。
- 1003 请求编码为 `etf`，没有 proto 请求消息；不要假设存在 `pb_equip_refine_req`。
- 1003 回包 `equip` 是单个对象，`multi` 是单值 `uint32`。
- 1004 请求字段为 `equip_id`、`target_level`；回包 `equip` 是单个对象，`multi` 是 `repeated uint32`（字段名单数但数组）。
- 1005 请求字段为 `equip_id`、`target_level`；回包只有 `equip` 和 `res_change`。
- 成功回包复用请求 `seq`；当前本机服实现的业务回复不设置 `pb_s2c.type`。
- 三个接口当前都只有静态契约，不能标记为“已捕获”“已解码回包”或“已操作验收”，除非后续提供对应运行时证据。

## 关键字段差异摘要

- 1003 的请求没有 proto 消息（`etf` / `schema=null`），而 1004、1005 的请求都是 protobuf。
- 1003、1004、1005 的回包 `equip` 都是单个 `pb_equip`，不是 `repeated`；这与 1001/1002/1006 的回包不同。
- 1004 的 `multi` 是 `repeated uint32`，字段名单数但必须按数组处理；1003 的 `multi` 是单值 `uint32`。
- 1004、1005 的请求都使用 `equip_id` + `target_level`；1003 的请求参数未在 proto 中定义，需结合客户端 Erl 编码。
- 1005 的回包最简，只有 `equip` 和 `res_change`，没有倍率或次数字段。
- 本组接口都不返回编队同步字段（`change_lineup` / `cur_pre_lineup`）。
- 批量接口 `1009 req_equip_refine_one_key_batch` 存在但不在本次文档范围内。
