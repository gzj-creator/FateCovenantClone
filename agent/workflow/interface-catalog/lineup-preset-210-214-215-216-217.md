## 传输信封

每条 TCP 消息前有 4 字节大端负载长度。握手阶段确定的 flags 决定是否加密，业务实现沿用现有网关，不在这里另定义握手、加密或签名。

请求由 `pb_c2s` 包裹：

```proto
message pb_c2s {
  uint32 seq = 1;   // 客户端请求序号，非零
  sint32 type = 2;  // 210 / 214 / 215 / 216 / 217
  bytes data = 3;   // 下表的请求 PB 或 ETF 参数
  int64 time_ms = 4;
}
```

`type` 使用 `sint32/ZigZag`，`data` 是请求消息的 protobuf wire bytes（214/215/216）或 ETF 编码参数（210/217）。

成功回包由 `pb_s2c` 包裹：

```proto
message pb_net_err {
  sint32 err = 1;
  bytes vars = 2;
  string stacktrace = 3;
}

message pb_s2c {
  uint32 seq = 1;
  uint32 type = 2;
  bytes data = 3;
  pb_net_err err = 4;
}
```

业务回复必须复用请求的 `seq`，`data` 放对应响应 PB。本仓库当前网关的成功回复写法是只发送 `{seq, data}`，不带 `type`；客户端按非零 `seq` 关联请求。不要假设响应 `type` 等于 210/214/215/216/217。`seq=0` 的帧属于推送。

失败回复沿用现有网关模式：省略 `data`，发送 `{seq, err: {err: <code>}}`。上述 `send` 模式见 [`personal-server/game/gateway.mjs`](../../../personal-server/game/gateway.mjs)。

## 实现交接约束

- 使用仓库现有 `personal-server/protocol/game-codec.mjs` 的 `codec.pack(schemaName, object)` / `codec.unpack(schemaName, bytes)`，保留 proto 的 snake_case 字段名。
- 214/215/216 使用 protobuf 编解码；210/217 使用 ETF 编码，无 protobuf schema。
- 210 请求无 protobuf 字段，仅 ETF 单参数；217 请求无 protobuf 字段且响应为 ETF 回退，形状未知。
- 214 请求与回包 schema 均为 `pb_custom_pre_lineup_list`。
- 215/216 请求使用 `pb_custom_lineup_*_req`，回包使用 `pb_custom_pre_lineup`（单个）。
- 215 请求 `index` 为 `uint64`，回包 `index` 为 `int64`；不要混用类型。
- 成功回包复用请求 `seq`；当前本机服实现的业务回复不设置 `pb_s2c.type`。
- `int64/uint64/sint64` 在仓库现有 codec 的 decode 输出中按字符串处理；构造时不要经过可能丢失精度的 JavaScript `number`。
- 五个接口当前都只有静态契约，不能标记为“已捕获”“已解码回包”或“已操作验收”，除非后续提供对应运行时证据。
- 当前没有实观请求/回包或客户端操作验收；所有字段语义仍需运行时验证。
